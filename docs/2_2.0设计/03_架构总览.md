# 当前架构总览

## 1. 目标

服务器是唯一权威。架构优先保证状态归属清晰、定时任务可恢复、跨模块副作用可追踪；不为尚未存在的微服务拆分预留额外复杂度。

## 2. 三层依赖

```text
gateway/   Wire、鉴权、会话、外部 payload 校验、Event → Push
    ↓
modules/   领域 owner 和游戏规则
    ↓
infra/     Store、Scheduler、消息总线、配置和通用算法
```

- `gateway` 可以依赖领域层并把外部 action 翻译成内部操作。
- `modules` 不能 import `gateway`，也不能 import 其他领域模块。
- `infra` 不包含具体游戏玩法。
- 组装根 `app.ts` 可以依赖所有层，但不承载领域计算。

外部 action、鉴权、会话注入和 payload schema 集中在 `gateway/routes.ts`。领域模块不感知 WebSocket 或客户端动作名。

## 3. 四项不变量

1. 每个持久集合只有一个领域 owner；其他模块不能直接访问它。
2. owner 之间不互相 import；同步协作走明确契约，广播通知走 Event。
3. 建造、训练、行军、战斗等未来任务统一登记 Scheduler，恢复逻辑由 owner 提供。
4. 资源产率、战斗属性等派生结果由 owner 算完再输出，不泄露内部可变对象。

架构测试自动检查模块互相 import、反向依赖 gateway、模块内定时器和集合 owner 唯一性。

## 4. 当前领域边界

完整 owner 表见 `PROJECT.md` §三。核心协作关系：

```text
Player ──建村──▶ Economy / Building / Military / Population / World
Building ──派生快照──▶ Economy / Population / Treasure
Movement ──到达──▶ Combat ──战果──▶ Military / PvE / Economy / Treasure
Research ──效果──▶ 对应数值 owner
领域事件 ──▶ Notifications 与 Gateway 推送
```

Combat 当前拥有 `battle` 集合，是有状态的逐 tick 模块；Movement 拥有在途部队。二者职责不能重新混为“行军模块顺便计算战斗”。

## 5. Command 与 Event 的使用边界

- Event：一件事已经发生，允许零到多个订阅者；不得依赖订阅者返回结果。
- Command：需要 owner 立即确认成败，或需要统一排队/审计的操作。
- 纯查询和单进程同步协作可以逐步收敛为强类型窄 Port；不要求为了形式解耦把所有调用都包装成自由字符串。
- 现有 CommandBus 在迁移完成前继续兼容，但新增契约应提供明确 payload/result 类型，禁止扩大 `any`。

## 6. 何时增加模块

只有新增了独立生命周期和持久状态 owner 才增加领域模块，例如邮箱、联盟成员表。以下情况不应新建模块：

- 新建筑、兵种、PvE、任务目录：优先增加 CSV 内容。
- 旧 owner 的新数值或派生加成：加入该 owner 的计算管线。
- 只用于展示的转换：放客户端 feature 或 `meta` 下发层。
- 单个模块内部变大：拆成同一 owner 目录下的 state/service/policy 文件，而不是创造新 owner。

## 7. 组装与注册

- `app.ts` 创建基础设施和领域实例，管理启动、恢复、热重载与刷档。
- `gateway/routes.ts` 是外部协议路由的唯一事实源。
- 新增 owner 时必须登记其生命周期和集合；未来应由应用 registry 派生初始化、恢复与刷档清单，避免多份手工列表。

## 8. 修改检查

- 新状态集合是否有唯一 owner？
- 领域层是否依赖了 gateway 或另一个领域模块？
- 外部 schema 是否只存在于 gateway？
- 定时任务是否能在重启后恢复？
- 新增字符串命令是否可以用已有强类型契约替代？
- 是否补了领域不变量和跨端链路测试？
