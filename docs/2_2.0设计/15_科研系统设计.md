# 科研/学院模块 · 架构设计

> **状态**：设计方案，待确认后进入实现阶段。
> **日期**：2026-08-11
> **范围**：科技树（军事/生产/社会三分支） + 学院建筑（多座 RP 池） + GM 面板（依赖编辑器 + 数值自定义） + 前端（学院详情页 + 科技树页）

---

## 一、核心概念与生命周期

```
学院建造 → 学院定期 tick（保底概率产出科研点/RP）→ 玩家在科技树页消耗 RP 开始研发
    → 研发计时结束 → 科技生效（数值注入 / 机制触发 / 解锁内容）
    → 新科技解锁后续科技的前置 → 循环
```

### 关键设计决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 科技模块拥有状态？ | 是，`research` 集合 | 每村科技进度 + RP 余额是模块独占状态 |
| 科技效果如何注入？ | 配置 + 注册表双轨 | 数值型走配置驱动（不改代码），机制型走注册钩子（写新代码） |
| 应用范围 | 默认本村，`scope=all` 影响所有村 | 少数科技需要跨村（如解锁关键建筑） |
| 科技依赖关系 | CSV `requires` 列 | 用科技 code 列出前置；无环校验启动期执行 |
| 多学院 | 共享 RP 池，每座加速生产 | 主城早期双学院造兵同理，多学院叠加 tick → 更快产出 RP |

## 二、数据模型

### 2.1 科研配置表 `config/research.csv`

```csv
id,code,name,branch,tier,requires,desc,effectType,effectKey,effectValue,scope,durationSec,rpCost,icon
```

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | int | 数字主键（跨表引用用） |
| `code` | string | 英文代码，程序内部用，勿改 |
| `name` | string | 显示名 |
| `branch` | enum | `military` / `production` / `social` |
| `tier` | int | 层级（1=基础, 2=进阶, 3=高级...），辅助前端树布局 |
| `requires` | string | 前置科技 code 列表，`\|` 分隔。如 `infantry_1\|spear_1` 表示两个都要。`OR` 语法：`infantry_1 OR cavalry_1` 表示满足其一即可。留空 = 无前置 |
| `desc` | string | 科技说明文本 |
| `effectType` | enum | 见下方「效果类型」表 |
| `effectKey` | string | 效果目标：资源名/兵种名/建筑 code/机制名 |
| `effectValue` | string | 效果数值（GM 可调）；机制型科技填 `mechanism` code，数值留查询参考 |
| `scope` | enum | `village`（本村） / `player`（所有村） |
| `durationSec` | int | 研发耗时（秒），CSV 固定值 |
| `rpCost` | int | 研发消耗科研点数 |
| `icon` | string | 图标基名 |

#### 效果类型 `effectType` 枚举

| effectType | effectKey | effectValue | 含义 | 实现方式 |
|------------|-----------|-------------|------|---------|
| `resource_rate` | wood/clay/iron/crop/gold | 倍率增量 | 该资源基础产率 +X% | 配置驱动：调 `economy.SetRateModifier` |
| `building_unlock` | 建筑 code | 1 | 解锁该建筑可建造 | 配置驱动：改 `building.GetBuildOptions` 的 unlock 判定 |
| `unit_unlock` | 兵种 code | 1 | 解锁该兵种可训练 | 配置驱动：改 `military.GetArmy` 的 trainable 列表 |
| `pop_growth` | — | 倍率增量 | 人口增长 +X% | 配置驱动：调 `population.SetTechGrowthMult` |
| `storage_cap` | wood\|clay\|iron\|crop | 倍率增量 | 仓储容量 +X%（乘在基础容量之上） | 配置驱动：调 economy 容量 |
| `combat_atk` | 兵种 code 或 `all` | 倍率增量 | 攻击力 +X% | 配置驱动：注入 military 派生管线 |
| `combat_def` | 同上 | 倍率增量 | 防御力 +X% | 同上 |
| `train_speed` | 兵种 code 或 `all` | 倍率增量 | 训练速度 +X% | 配置驱动：注入 military.trainFactor |
| `build_speed` | 建筑 code 或 `all` | 倍率增量 | 建造速度 +X% | 配置驱动：注入 building.buildTime |
| `march_speed` | — | 倍率增量 | 军队移动速度 +X% | 配置驱动：注入 movement 的基础速度 |
| `carry_cap` | — | 倍率增量 | 军队运载 +X% | 配置驱动：注入 movement 运载量 |
| `mechanism` | 机制 code | — | 触发特殊机制代码 | 注册表钩子：执行 `MechanismRegistry[code](villageId)` |

> **机制型科技**（`effectType=mechanism`）：`effectKey` 填机制 code，`effectValue` 填该机制所需参数（JSON 或逗号分隔数)。机制 code 在 `research/mechanisms.ts` 中注册处理器。新增机制 = 在此文件加函数 + 在 registry 登记，**不改 ResearchModule 主逻辑**。

### 2.2 学院参数表 `config/academy.csv`

```csv
level,checkIntervalSec,baseProbability,probabilityGainPerFail,maxProbability
```

| 列 | 说明 | 默认值示例 |
|----|------|-----------|
| `level` | 学院等级 | 1 |
| `checkIntervalSec` | 两次判定间隔（秒），随等级递减。多学院时加速=间隔/学院数 | 3600 → 1800 → 900 |
| `baseProbability` | 每次判定产出一个 RP 的基础概率（0-1） | 0.10 |
| `probabilityGainPerFail` | 每次失败后增加的概率（0-1），保底核心 | 0.02 |
| `maxProbability` | 概率上限（保底线） | 0.30 |

> 学院升级消耗**仅走 building_levels.csv 的 cost 体系**（同其他建筑），不消耗 RP。

> **保底模型**：`P(success) = min(baseProbability + failStreak × probabilityGainPerLevel, maxProbability)`。成功产出一个 RP 后 `failStreak` 重置为 0。所有学院共享同一个 `failStreak`（因为共享 RP 池）。

### 2.3 学院也是建筑

- 在 `buildings.csv` 中新增 `academy` 行：`zone=inner`，有建造前置（如 main Lv3）
- 在 `building_levels.csv` 中新增 `academy` 的逐级成本/耗时（走标准建造流程，不消耗 RP）
- 学院建造/升级/拆除触发 `building.Built/Upgraded/Demolished` 事件 → ResearchModule 订阅并更新 academy 参数
- 拆光所有学院后 RP 生产暂停，但已完成科技效果不清除

## 三、运行时状态（`research` 集合，per-village）

```ts
interface ResearchState {
  villageId: string;
  rp: number;                          // 科研点余额
  researching?: {                      // 当前研发中的科技
    code: string;
    startedAt: number;                 // 开始时间戳
    durationMs: number;                // 研发耗时
  };
  completed: string[];                 // 已完成科技 code 列表
  academy: AcademyState;               // 学院生产力状态
}

interface AcademyState {
  failStreak: number;                  // 连续失败次数（驱动保底概率）
  lastCheckTime: number;               // 上次判定时间（用于惰性回溯）
  highestLevel: number;                // 村内最高学院等级（影响判定参数）
  academyCount: number;                // 学院数量（影响判定间隔加速）
}
```

### 跨村共享（player 级别效果）

当科技 `scope=player` 时，效果需要注入同玩家所有村庄。这需要一个轻量的跨村查询：

```ts
// app.ts 中给 ResearchModule 注入
interface PlayerVillageMap {
  villagesOf(playerId: string): string[];   // 返回该玩家所有村庄 id
}
```

研究模块内部维护一个 `playerEffects` 缓存（重启时从各村的 `completed` 列表重建），跨村效果在 tick 时批量推送到所有村。

## 四、科技点（RP）生产流程

```
每个 tick（Scheduler 驱动，间隔 = academy.csv checkIntervalSec / academyCount）
  ↓
读取 AcademyState → 根据 failStreak 计算当前概率
  ↓
roll(LcgRng) → success?
  ├─ Yes → rp += 1; failStreak = 0; 推送 RP 变化
  └─ No  → failStreak += 1; 调度下一次 tick
```

### 关键细节

1. **Scheduler 调度**：用 `Scheduler.schedule(ms, callback, owner)`，owner = `research:${villageId}`，重调度时先 `cancelByOwner` 再重新 schedule。
2. **惰性回溯**：服务器重启后，根据 `lastCheckTime` 计算从上次判定到现在应该执行多少 tick，一次性结算（防止重启丢失离线 RP）。
3. **多学院加速**：判定间隔 = `checkIntervalSec / academyCount`（有 2 座学院 = 间隔减半 = 判定频率翻倍）。
4. **等级影响**：用本村 `highestLevel` 查询 `academy.csv` 的 `baseProbability`、`probabilityGainPerLevel`、`maxProbability`。

## 五、模块集成设计

### 5.1 ResearchModule 骨架

```ts
// packages/server/src/modules/research.ts

export const MechanismRegistry: Record<string, (ctx: MechanismContext) => void> = {};
export function registerMechanism(code: string, handler: (ctx: MechanismContext) => void): void {
  MechanismRegistry[code] = handler;
}

// 在 init() 中注册默认机制
export class ResearchModule {
  static NAME = 'research';
  
  // 命令
  // research.GetState       → 返回 ResearchState（给学院详情页）
  // research.GetTechTree    → 返回全部科技定义 + 每科技的研发状态（可研/已研/前置未满足）
  // research.StartResearch  → 扣 RP，开始计时，调度 done
  // research.CancelResearch → 按剩余进度比例返还 RP，向下取整，取消计时
  
  // 事件
  // research.TechCompleted  → 科技研发完成，广播
  // research.RpChanged      → RP 变化，推客户端刷新
  
  // 内部
  // tickRp(villageId)       → 执行一次 RP 判定（由 Scheduler 驱动）
  // applyTech(villageId, code) → 科技生效：分派到配置/机制处理器
  // rebuildPlayerEffects(playerId) → 重建跨村效果缓存
}
```

### 5.2 与现有模块的双向交互

```
Building  → research.SetAcademyParams（academy 建造/升级/拆除时）
Building  ← research（tech 解锁新建筑时，通过 building.GetBuildOptions 返回的 unlock 判定）
Military  ← research（tech 解锁兵种 + 攻击/防御/训练速度加成）
Economy   ← research（resource_rate / storage_cap 加成）
Population ← research（pop_growth 加成）
Movement  ← research（march_speed / carry_cap 加成）
Meta      ← research（GetGameConfig 下发科技列表给前端渲染科技树）
GM        → research（覆盖层编辑科技依赖/数值）
```

### 5.3 科技效果注入实现方式

**数值型**（配置驱动，不改 ResearchModule 核心）：
```ts
// research.ts 内部
private applyNumericEffects(villageId: string): void {
  for (const code of state.completed) {
    const tech = this.config.research[code];
    switch (tech.effectType) {
      case 'resource_rate':
        void this.commands.send({ name: 'economy.SetRateModifier', /* ... */ });
        break;
      case 'combat_atk':
        void this.commands.send({ name: 'military.SetCombatMult', /* ... */ });
        break;
      // ... 所有数值型均在此分派
    }
  }
}
```

**机制型**（注册表驱动，加新机制不改此处）：
```ts
private applyMechanism(villageId: string, code: string): void {
  const tech = this.config.research[code];
  if (tech.effectType !== 'mechanism') return;
  const handler = MechanismRegistry[tech.effectKey];
  if (handler) {
    handler({ villageId, tech, commands: this.commands, bus: this.bus, config: this.config });
  }
}
```

新机制只需要在 `research/mechanisms.ts` 中：
1. 写 handler 函数
2. `registerMechanism('my_mechanism', myHandler)`

不改 ResearchModule。

## 六、GM 面板设计

### 6.1 科技依赖编辑器（GM 子页 `/gm/research`）

在现有 GM 面板 `BALANCE_TABLES` 中新增：

```ts
research: {
  file: 'research.csv', key: 'id',
  numeric: ['tier', 'effectValue', 'durationSec', 'rpCost'],
  labels: ['id', 'code', 'name', 'branch', 'tier', 'requires', 'effectType', 'effectKey', 'scope'],
}
```

**依赖关系可视化**：GM 面板渲染科技表格时，`requires` 列渲染为可编辑文本，用 `|` 或 `OR` 分隔多个前置。

额外功能：
- 一个「依赖图预览」按钮，以 ASCII/文字形式展示当前的依赖树，帮助检查循环引用
- 启动期 `validateGameConfig()` 新增：科技依赖无环检查、branch 枚举校验、前置科技 must exist

### 6.2 数值科技的自定义

所有 `effectType != 'mechanism'` 的科技，其 `effectValue` 列在 GM 面板中显示为可编辑输入框。值类型取决于 effectType：
- 倍率类（rate/speed 等）：float，如 `0.15` 表示 +15%
- 解锁类（unlock）：通常为 `1`（布尔），但保留数字灵活性
- 容量类（storage_cap）：float 倍率

### 6.3 学院参数面板

`academy.csv` 已是独立的 BALANCE_TABLE 条目，在 GM 面板中显示为单独的 section（类似 trade_center/merc_camp）。每个 level 一行，全部列可编辑。

### 6.4 覆盖层热重载

科技参数和学院参数的修改通过现有的 `data/balance_overrides.json` 机制 → 编辑 → save → `reloadConfig()` 即时生效。已完成的科技效果会在 `reloadConfig` 后通过 `rebuildPlayerEffects` 自动重新计算推送。

## 七、启动期校验（config.ts `validateGameConfig` 新增）

1. **科技依赖无环**：拓扑排序检查 `requires` 引用不能形成循环
2. **前置科技存在**：`requires` 中引用的 code 必须在 research.csv 中存在
3. **branch 值合法**：`military | production | social`
4. **机制 code 已注册**：`effectType=mechanism` 时 `effectKey` 在 `MechanismRegistry` 中已注册（warn，不硬阻止部署）
5. **scope 值合法**：`village | player`
6. **academy 与 buildings 一致**：`academy.csv` 中 level 数量 ≤ `building_levels.csv` 中 academy 的 maxLevel

### 8.3 前端数据流

1. 进入科技树 → `research.GetTechTree` → 返回全部科技的 JSON（含 id/code/name/branch/tier/requires/desc/effect*/scope/icon） + 每科技的研发状态（`locked` / `available` / `researching` / `completed`）
2. 点击开始研发 → `research.StartResearch { techCode }` → 后端扣 RP + 计时
3. RP 变化由 `research.RpChanged` 推送 → 前端刷新头顶 RP 数
4. 研发完成由 `research.TechCompleted` 事件 → 前端刷新科技树状态 + 可能通知其他页签解锁了新建筑/兵种

## 十一、已确认的设计决策

| # | 问题 | 确认 |
|---|------|------|
| 1 | 科技研发耗时 | **CSV 固定时间**：`research.csv` 新增 `durationSec` 列，每个科技独立配置 |
| 2 | 学院升级消耗 | **仅资源**（同其他建筑），走 `building_levels.csv` 的 cost 体系。升级期间正在研发的科技不受影响、继续计时 |
| 3 | 取消研发返还 | **按剩余进度比例返还**：`返还 RP = floor(已完成 RP 成本 × 剩余时间比例)`，向下取整。已扣的不退 |
| 4 | scope=player 跨村 | **自动生效**：新村庄创建后，`player.Register` / `found-village` 事件触发 `research.InitNewVillage`，把玩家所有 `scope=player` 的已完成科技效果注入新村庄 |
| 5 | 前端科技树 | **新增顶级 tab「科技」**（在村庄/军队/地图/报告右侧），学院建造后才出现。同时学院详情页保留「进入科技树」入口 |

- 拆光所有学院后 tab 隐藏，但已完成科技效果不清除（只停止 RP 生产）
