# 阶段化战斗系统方案策划书

## 1. 文档目的

本文将讨论中确定的战斗规则固化为可模拟、可测试、可实现的方案。它是新战斗系统的玩法基线，不代表已经替换线上战斗。

当前线上战斗是服务端权威的逐 Tick 系统，位于 `packages/server/src/modules/combat/`。本方案采用阶段化结算，正式切换前必须先完成独立模拟器、历史战报回放和数值验证。

## 2. 设计目标

- 让骑兵冲锋、远程打击和近战阶段具有明确的战术分工。
- 用兵种的近战攻防、远程攻防、生命值和特性形成编队差异。
- 伤亡结果有阶段解释，战报能说明每一步损失来源。
- 伏击、掠夺、野外遭遇和攻城拥有不同的结束逻辑。
- 特性目标有随机性，但分配均匀、可重放、不可被客户端操纵。
- 不保存单个士兵的伤口状态，避免引入复杂伤兵存档和人口迁移。

## 3. 非目标

- 本阶段不新增兵种、建筑、宝物或科技类型；兵种战斗属性可按统一价值模型做平衡校准。
- 本阶段不修改行军速度、视野、人口上限和资源系统。
- 不把客户端随机数作为战斗依据。
- 不在模拟和测试完成前直接替换生产战斗。

## 4. 参战数据

每个兵种至少拥有：

| 字段 | 作用 |
|---|---|
| `meleeAtk` | 近战攻击力 |
| `meleeDef` | 近战防御力 |
| `rangedAtk` | 远程攻击力 |
| `rangedDef` | 远程防御力 |
| `hp` | 生命池计算用的单位生命值，必须大于 0 |
| `count` | 当前存活单位数量 |
| `popCost` | 单位占用的人口；用于映射有效战斗人口 |
| `traits` | 该兵种拥有的特性 |

`popCost` 同时参与战斗影响力映射，但不直接放大单兵攻防与生命值；它代表同人口下该兵种应有多少“战斗席位”。佣兵的经济 `popCost=0` 在战斗影响力中按 1 个战斗席位计算，避免出现零战力。

### 4.1 基础属性价值与人口校准

为了避免单纯堆攻击或生命值造成建造陷阱，基础战斗分值只计算五项战斗属性，不计算特性、速度、负重、造价和科技：

```text
attackValue = meleeAtk × 1.00 + rangedAtk × 1.10
defenseValue = meleeDef × 0.85 + rangedDef × 0.75 + hp × 0.65
baseCombatValue = attackValue + defenseValue
valuePerPopulation = baseCombatValue ÷ popCost

quality = clamp((valuePerPopulation ÷ 200)^1.15, 0.65, 1.55)
attackQuality = clamp((attackValue ÷ (popCost × 100))^1.15, 0.65, 1.55)
defenseQuality = clamp((defenseValue ÷ (popCost × 100))^1.15, 0.65, 1.55)

effectivePopulation = count × popCost × quality
effectiveAttackPool = count × attackQuality × attack
effectiveDefensePool = count × defenseQuality × defense
```

指数大于 1 是为了让高质量兵种的有效人口增长快于线性人口；攻击质量与防御质量分轴计算，使高攻脆皮强化攻击侧、高防低攻强化防御侧，攻防差异不会被一个总分抹平。当前常规战斗兵种的基础分值约为每人口 180–217，高科技复合兵装约为 240–263，形成约 10%–30% 的基础溢价；`quality` 的上下限用于防止极端配置失控。特性价值单独评估，不回填到上述分值。攻城器械、侦察兵、首领、拓荒者和冒险者属于功能单位，不与常规战斗兵种共用该区间。

### 4.2 生命伤亡池

生命值是阶段/步骤伤亡池，不是单个士兵的持续 HP。

每一个步骤或每一轮开始时重新计算：

```text
totalHp = Σ（当前兵种数量 × 兵种 hp）
```

步骤结束后只保留整数兵力。剩余单位进入下一步骤时重新计算生命池，不保留个体受伤状态。

## 5. 通用步骤算法

每一个冲锋步骤、远程步骤、近战轮次和最终阶段结算轮次都遵循同一顺序：

1. 读取步骤开始时双方仍存活的兵力。
2. 从当前存活兵力中重新进行特性目标分配。
3. 应用特性、科技、宝物及阶段加成。
4. 计算本步骤所需的总攻击力、总防御力和目标生命池。
5. 双方同时计算本步骤伤害；同一步骤内不因中途阵亡重新计算。
6. 将伤害转换为目标总阵亡数。
7. 按兵种理论损失分配阵亡单位，并限制在目标现有兵力内。
8. 进入下一步骤或根据战斗模式结束。

基础伤害规则：

```text
rawDamage = attackerPower² ÷ (attackerPower + defenderPower) × phaseCoefficient
lossRatio = min(1, rawDamage / targetTotalHp)
phaseRealLoss = ceil(targetTotalUnits × lossRatio)

online Lanchester state = effectivePopulation
onlineRealLoss ≈ onlineEffectiveLoss ÷ 目标平均 influencePerUnit
```

攻击力为 0 或伤害系数为 0 时伤害为 0；防御力为 0 的合法战斗按 `rawDamage = attackerPower × phaseCoefficient` 计算。
该除法公式没有“攻击不超过防御就完全不掉血”的硬阈值，攻击优势仍会随防御提高而递减，适合 4X 战斗中持续消耗和人数优势叠加。阶段模拟器使用有效攻防池、真实生命池和阶段伤亡；线上逐 Tick 引擎则用有效战斗人口推进兰开斯特方程，再把有效伤亡换回真实单位。因此 `popCost=2` 的单位不会因为真实数量较少而被错误地当成弱小部队。

### 5.1 兵种损失分配

对目标方每个兵种计算：

```text
quota[i] = count[i] × lossRatio
baseLoss[i] = floor(quota[i])
remaining = totalLoss - Σ baseLoss[i]
```

`remaining` 个单位按小数余数从高到低补足；余数相同时使用服务端战斗随机源选择。最终所有兵种损失之和必须等于 `totalLoss`，不能超过目标总兵力。

例如五个兵种各 2 个、损失比例 10%，总兵力 10，最终只损失 1 个单位，并在五个兵种之间随机选择，而不是每个兵种各损失 1 个。

## 6. 阶段一：骑兵冲锋

骑兵冲锋只进行一次，不进入重复冲锋循环。冲锋攻击力使用：

```text
有效骑兵攻击 = 骑兵近战攻击力 ×（1 + 冲锋加成）
```

### 步骤一：骑兵对冲

- 双方当前骑兵互相计算近战攻击和近战防御。
- 双方同时承受伤害。
- 伤害只作用于对方骑兵生命池。

### 步骤二：骑兵冲击近战步兵

- 使用幸存骑兵攻击敌方近战步兵。
- 目标防御使用近战防御。
- 骑兵在此步骤不承受步兵反击。

### 步骤三：骑兵冲击远程步兵

- 仅当敌方近战步兵已经清空时执行。
- 使用幸存骑兵攻击敌方远程兵。
- 骑兵已经冲入远程兵阵列，目标防御使用近战防御。
- 骑兵在此步骤不承受远程反击。

没有对应目标的步骤直接跳过。冲锋各步骤都必须根据当前冲锋目标重新计算目标生命池和总防御。

## 7. 阶段二：远程打击

- 每一方独立选择远程打击目标：敌方仍有近战兵时，目标为敌方近战兵；敌方没有近战兵时，目标改为敌方远程兵。
- 冲锋阶段结束后仍存活的近战骑兵属于近战兵力池，会和其他近战兵一起成为远程打击目标。
- 无论目标是近战兵还是远程兵，远程打击统一使用目标的远程防御力。
- 双方根据各自的目标池独立计算，因此可能出现一方射击近战兵、另一方射击远程兵的情况。
- 双方同时计算伤害。
- 伤害转换为目标兵力池的总损失，再按兵种分配。

## 8. 阶段三：近战互殴

双方各自形成一个兵力池，包含当前剩余的骑兵、近战兵和远程兵。

- 所有兵种使用近战攻击和近战防御。
- 远程兵在此阶段转换为近战攻防，但保留当前单位数量。
- 总生命池包含所有剩余兵种的生命值。
- 每轮重新分配特性、重新计算总攻防和生命池。
- 每轮按统一损失比例等比例分配兵种伤亡。

近战阶段进行配置规定的轮数。若一方全军归零，立即结束；若轮数结束时双方仍有兵，则按战斗模式处理。

## 9. 战斗模式结果

| 模式 | 近战阶段结束仍有双方存活时的结果 |
|---|---|
| 野外伏击战 | 防守方胜利，进攻方撤退且无收获 |
| 掠夺战 | 防守方胜利，进攻方撤退且无收获 |
| 野外遭遇战 | 判定平手，双方撤退，不产生掠夺 |
| 攻城战 | 进入最终阶段，必须分出胜负 |

如果阶段一至三已经使一方全军归零，则不再使用模式兜底，直接按实际胜负结算。

## 10. 攻城最终阶段

最终阶段使用当前双方所有剩余兵力，远程兵仍按近战攻防参与比较。依次比较：

1. 总近战攻击力；
2. 攻击力相等时比较总近战防御力；
3. 防御力相等时比较总生命值；
4. 三项都相等时防守方获胜。

非完全相等时，使用决定胜负的同一指标计算胜方战损：

```text
winnerLossRatio = loserMetric / winnerMetric
winnerLoss = ceil(winnerCurrentUnits × winnerLossRatio)
```

胜方损失后至少保留 1 个单位。败方在最终阶段全灭。

如果用于最终防御力比较的败方防御力为 0，则胜方损失比例为 0，胜方 100% 存活。

三项完全相等时：

- 防守方获胜；
- 进攻方全灭；
- 防守方随机保留 1 个实际单位，其余兵力按失败结算。

该随机保留单位必须记录在战报中，并使用服务端可重放随机源。

## 11. 兵种特性

每个拥有特性的士兵在每个阶段、步骤或轮次开始时，从当前仍存活且符合条件的敌我单位中随机选择一次目标。

### 11.1 均匀目标分配

目标分配必须满足：任意两个目标收到的同类特性影响数量最多相差 1。

推荐算法：

1. 建立符合条件的目标单位序列；
2. 使用战斗随机种子打乱目标序列；
3. 按循环顺序把特性来源单位分配到目标序列；
4. 目标不足时从序列开头重新循环。

例如 15 个枪兵影响 10 个骑兵时，10 个骑兵至少各受到 1 次影响，其中 5 个随机骑兵再受到第 2 次影响。

### 11.2 加成合并

同一目标收到多个同类特性时先相加，再计算有效数值：

```text
effectiveMultiplier = max(0, 1 + Σ modifiers)
```

因此，两个 `-30%` 攻击力特性命中同一目标时，目标保留 `40%` 攻击力，而不是 `49%`。采用加法的原因是每个特性都代表固定的百分点变化，规则更容易解释、配置和复盘；同时与 Debuff 最低降至 0 的约束一致。Buff 不设上限。没有符合条件的目标时，该特性本轮浪费。

不同属性分别计算。例如近战攻击、远程攻击、近战防御和远程防御各自汇总本属性的修正，不把攻击修正错误地应用到防御或其他阶段。

特性只影响其声明的属性，例如近战攻击、远程攻击、近战防御或远程防御。特性来源在下一轮阵亡后不再生效。

### 11.3 随机与回放

- 随机只能由服务端产生；客户端不得提交结果。
- 随机流按 `battleId + phase + step + round + traitCode` 隔离。
- 战斗恢复、战报回放和自动测试必须得到相同的特性分配结果。
- 实现时应按兵种数量聚合分配，不能为每个士兵创建独立运行时对象。

## 12. 配置中心参数

所有平衡项均进入配置中心，不写死在客户端：

| 参数 | 说明 |
|---|---|
| `unit_traits.csv` 中的 `cavalry_charge_atk` | 非侦察骑兵冲锋攻击加成（按兵种特性配置） |
| `combat_phase_cavalry_vs_cavalry_coeff` | 骑兵对冲伤害系数，当前 0.18 |
| `combat_phase_cavalry_vs_melee_coeff` | 骑兵冲击近战伤害系数，当前 0.20 |
| `combat_phase_cavalry_vs_ranged_coeff` | 骑兵冲击远程伤害系数，当前 0.25 |
| `combat_phase_ranged_strike_coeff` | 远程打击伤害系数，当前 0.30 |
| `combat_phase_melee_round_coeff` | 近战每轮伤害系数，当前 0.20 |
| `combat_influence_reference_value` | 基础战斗价值/人口参考点，当前 200 |
| `combat_influence_quality_exponent` | 有效战斗人口质量指数，当前 1.15 |
| `combat_influence_min_quality` / `combat_influence_max_quality` | 有效战斗质量上下限，当前 0.65 / 1.55 |
| `combat_value_*_weight` | 五项基础战斗属性权重：1 / 1.1 / 0.85 / 0.75 / 0.65 |
| `battle_sim_melee_rounds` | 近战阶段轮数 |
| `combat_phase_compare_epsilon` | 攻防/生命值相等的浮点误差 |
| `combat_phase_min_survivor_units` | 胜方最少保留单位数，默认 1 |

现有 `combat_strength`、城墙、宝物和兵种特性参数仍保留，但必须明确它们在新阶段中的应用顺序。

## 13. 状态、协议和结算影响

- 战斗仍由 Combat 模块作为唯一 owner，服务端保持权威。
- Movement 只负责把参战快照交给 Combat，不重新实现阶段结算。
- 战斗结果继续通过 `BattleEnded` 传递给 Movement、Military、Population、PvE 等模块。
- 需要扩展战报以记录阶段、步骤、双方总攻防、生命池、总损失和特性摘要。
- 阶段化战斗中的 HP 只存在战斗状态内；如果不增加旧军队或村庄字段，不应触发存档迁移。
- 正式切换时应为进行中的旧战斗保留兼容处理，不能直接用新规则解释旧战斗快照。

### 13.1 独立模拟器（当前交付形态）

当前先以服务器内无状态 `battle-simulator` 模块交付，入口为 `/battle-simulator`，并通过 `battleSimulator.GetCatalog` / `battleSimulator.Simulate` 提供目录和模拟请求。它只读取启动时解析的 CSV（兵种、`unit_traits`、PvE 守军、科技、宝物和全局常量），不读取或写入玩家、村庄、行军、战斗存档，也不调用线上 Combat/Military/Movement 模块。随机种子由调用者指定即可复盘；正式替换线上战斗前，先用该页面和后端纯函数完成数值验收。

兵种生命值写在 `units.csv.hp`，模拟器特性写在 `units.csv.simTraits`；雇佣兵使用 `mercenaries.csv.hp/simTraits`，PvE 守军使用 `pve_defenders.csv.hp/traits`。配置中心的兵种、特性、雇佣兵、PvE 守军和阶段伤害系数均可编辑，保存后只影响新的模拟请求。

## 14. 验收测试

### 14.1 规则测试

- 生命值必须大于 0；伤害不能为负；伤亡不超过现有兵力。
- 伤亡总数统一向上取整，兵种损失之和严格等于总损失。
- 五个兵种各 2 个、损失 10% 时只损失 1 个单位。
- 骑兵冲锋只执行一次，步骤二和步骤三的骑兵不受反击。
- 骑兵冲击远程兵时使用远程兵的近战防御，不使用远程防御。
- 骑兵每一步按照当前目标重新计算生命池和防御。
- 远程阶段双方都有近战时射击近战兵；一方没有近战时射击远程兵；双方都没有近战时远程互射。
- 远程阶段无论射击近战兵还是远程兵，均使用目标的远程防御；冲锋后幸存骑兵计入近战目标池。
- 近战阶段所有剩余兵种都使用近战攻防。
- 攻城最终阶段按攻击→防御→生命值顺序决胜。
- 最终阶段胜方至少保留 1 个单位；败方防御力为 0 时胜方不损失。
- 三项完全相等时防守方获胜并保留 1 个随机单位。

### 14.2 特性和随机测试

- 目标分配中任意两个目标收到的影响数量最多相差 1。
- 特性目标只来自当前存活单位。
- 多个同类 Debuff 在同一目标上相加：两个 `-30%` 保留 40%，结果最低为 0。
- 没有合格目标时特性浪费。
- 相同战斗种子重放结果完全一致。
- 双方同时结算时不会出现先手额外伤亡。

### 14.3 集成测试

- 纯骑兵、纯近战、纯远程和混合编队。
- 骑兵数量不足、骑兵碾压、无敌方骑兵。
- PvE、玩家村庄、增援、王国 NPC 军队。
- 伏击、掠夺、遭遇战和攻城。
- 城墙、宝物、科技、兵种特性叠加。
- 服务器重启后战斗继续，战报和随机结果不变。
- 旧战斗快照不会被新引擎错误解析。

### 14.4 数值策略验收

采用 `seed=17`、无城墙/科技、阶段伤害系数使用当前配置的条件，重点阵容结果如下。阶段模拟的 `field` 模式不强行宣告胜负，表中以战后剩余兵力和人口影响力判断优势：

| 对局（双方约 100 经济人口） | 战后结果 | 设计解释 |
|---|---|---|
| 100 盾墙军团 vs 100 盾墙军团 | 94 vs 94 | 基准镜像基本对称 |
| 100 鹰旗突击队 vs 50 鹰旗禁卫 | 94 vs 32 | 高攻方能拆重甲，但禁卫仍能拖长战斗 |
| 33 冲角骑兵 vs 100 拒马长矛（含反骑兵特性） | 27 骑兵 vs 92 长矛 | 同人口硬克制使长矛在有效人口上反超骑兵；关闭特性时为 27 vs 52，说明特性是独立增量 |
| 50 拒马长矛 + 50 破阵斧手 vs 33 冲角骑兵（不计特性） | 29 + 27 vs 18；有效人口 60.7 vs 50.4 | 矛兵承伤、斧兵输出形成基础数值混编优势；加入特性后为 41 + 37 vs 9，特性收益单独叠加 |
| 33 战獠王骑 vs 100 盾墙军团（不计特性） | 27 vs 38；有效人口 111.1 vs 38.5 | 高科技骑兵的单位数更少，但按人口质量映射后仍保留明显战力溢价；同时没有无损清场 |

同样的阵容应同时在 `/battle-simulator` 和线上逐 Tick 引擎做回归；线上引擎额外验证 `popCost=2/3/4` 单位按有效人口折算后，不会因真实单位数较少而错误失去兰开斯特人数优势。

## 15. 实施阶段

1. 建立纯函数阶段化战斗模拟器，不接入生产 Movement。
2. 补齐兵种 HP、阶段系数和特性目标分配的配置结构。
3. 用历史战斗组合进行批量模拟，检查胜率、战损和阶段贡献。
4. 完成 Combat 结算与战报扩展，保留旧战斗兼容路径。
5. 完成 PvE、PvP、增援、NPC 和四种战斗模式的集成测试。
6. 增加灰度开关，仅在测试环境和指定战斗使用新规则。
7. 通过完整验证后，再安排正式切换和旧战斗收尾策略。

## 16. 结论

该方案适合发展为正式战斗系统。它的核心取舍是：生命值只承担阶段伤亡池职责，兵种不保存个体伤口；战斗随机性主要来自均匀约束下的特性目标选择；攻城战通过最终攻防/生命值顺序保证一定分出胜负。

在进入编码前，必须先完成模拟器和数值回放，尤其验证骑兵免费冲锋、远程兵在前排消失后的转火、最终阶段惨胜比例和无限 Buff 的极端场景。
