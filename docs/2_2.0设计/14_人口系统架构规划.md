## 〇、一句话结论

**人口是一块全新的独占状态（currentPop / woundedPool / 劳动力与繁荣度快照），说得出唯一 owner → 新建模块 `modules/population.ts`。** 它向 economy 登记一条真实的 `civilian_pop` 粮食维护并推送劳动力产率修正器（决策 C1），向 economy 只读拉取「粮食上下文」来算软上限；与 building 通过既有 `building.Built/Upgraded` 事件 + 一个新的只读拉取命令 `building.GetLaborContext` 解耦。**economy↔population 的双向数据关系用「单向写 + 惰性只读 + 快照」拆成无环调用图**（§二·2.4 是本文重点）。伤兵治愈走 Scheduler，绝不在模块内用定时器。

同时收掉两处历史问题：① building 现在上报的 `economy.SetUpkeep(source:'population')` 实为**建筑维护**（`sumPop(lv)`），语义错名，本次改名 `source:'building'` 让出语义空间给民用人口；② economy 有 `rateModifiers` 数组却无对外 setter，本次补 `economy.SetRateModifier`，让人口的劳动力增幅能注入产率派生管线（铁律#4）。

## 一、Step 1 · 需求分析

### 1.1 新增/变化的状态（谁拥有）

| 状态 | 说明 | owner |
|------|------|-------|
| `currentPop` | 当前人口（不含伤兵），惰性增长/减员 | **Population（新）** |
| `woundedPool[]` | 伤兵队列 `{count, healAt}`，Scheduler 到点回补 | **Population（新）** |
| `lastTick` | 上次惰性结算时间戳 | **Population（新）** |
| `prosperity` | 繁荣度快照（building 算好后同步给它） | **Population 缓存**（真源在 Building 的等级） |
| 劳动力上下文缓存 | 各 laborAmplified 建筑的 `{kind,level,resource}`（从 building 拉取的快照） | **Population 缓存**（真源在 Building） |
| 派生：软上限 L / 增长率 / 各建筑劳动倍率 / 治疗 λ | 全部在 Population 内部算，对外只给结果 | **Population 内部计算** |

**结论**：`currentPop`/`woundedPool` 是一块**全新的、有明确唯一 owner 的独占状态**——按扩展决策树总闸「说得出 owner 就加文件」→ **新建 `modules/population.ts`**。繁荣度与建筑等级不是它的状态（真源在 Building），它只缓存快照。

### 1.2 读/改的既有状态（都不直接碰，只走 Command/Event）

- **Economy**（owner=economy）：
  - 人口向它登记真实粮耗 → 既有 `economy.SetUpkeep`（新 source=`civilian_pop`）。
  - 人口把劳动力产率增幅注入它的派生管线 → **新增 `economy.SetRateModifier`**。
  - 人口读「粮食上下文」算软上限 → **新增 `economy.GetCropContext`**（只读，不回调）。
- **Building**（owner=building）：
  - 完工/升级时人口需重算繁荣度与劳动力 → 人口订阅既有 `building.Built`/`building.Upgraded` 事件，再**新增只读命令 `building.GetLaborContext`** 拉取 `{prosperity, buildings[]}` 快照。
  - building 现有 `reportPopulation()` 的 `SetUpkeep(source:'population')` **改名** `source:'building'`（见〇结论）。
- **Military**（owner=military）：
  - 训练前扣人口 → **人口 `population.ConsumePop`**；不足拦截。
  - 练兵速率随劳动力 → 读 `population.GetLaborMult(barracks/stable/workshop)` 调 `trainSec`。
  - 锻造速率（`UpgradeSmithy`）随劳动力 → 读 `population.GetLaborMult(smithy)`（**注意：本项目暂无独立 smithy/academy 模块，锻造在 military 内**）。
  - 解散军队 → **人口 `population.ReturnPop`**（100% 返人口，不返资源）。
- **Combat**（owner=combat）：
  - 结算时把攻守双方各自损失（它已算好 `attackerLosses`/`defenderLosses`）发给**各自村庄的人口** → **`population.AddWounded`**。**不再需要人口防御快照**（防御效应已删）。

### 1.4 客户端影响

- 村庄页新增「人口/文明活力」面板：当前人口、软上限、增长速率、伤兵数与治愈倒计时、各项劳动力加成百分比（产率/研究/练兵/锻造/建造）。
- 客户端**不持有权威人口**：`GetPopulation` 拿快照（含 `growthPerHour` 与各 `healAt`），客户端像资源倒计时那样**本地外插**当前人口显示；`PopulationChanged` push 用于离散事件（训练扣人、伤兵登记、治愈、减员）后校正。
- 训练面板：显示每兵 `popCost`（meta 下发），人口不足时按钮灰显/报 `insufficient_population`。
- 新增「解散军队」入口 → `DisbandTroops`。

### 1.5 朴素做法会踩的铁律雷（预警）

- ❌ **让 population 直接读 economy 的 `resources`/`baseRate` 或直接读 building 的 `placed`** → 违反铁律#1。必须走 `GetCropContext` / `GetLaborContext` 拿快照。
- ❌ **economy 反过来同步调用 population 算劳动倍率再算产率** → 形成运行时环。正确：population **单向**把倍率经 `SetRateModifier` 推给 economy，economy 只存不问（见 §二·2.4）。
- ❌ **在 population 内用 `setTimeout` 计伤兵治愈** → 违反铁律#3。每个伤兵批次一个 `scheduler.schedule`，`resume()` 重登记。
- ❌ **让 combat 直接算 `popCost × ratio` 生成伤兵数** → combat 不该懂人口。combat 只传它已有的原始损失，population 用 config 算（铁律#4）。
- ❌ **把繁荣度/劳动倍率/软上限落库成 population 的权威字段** → 它们是派生快照；繁荣度真源是 building 等级。population 缓存可以，但重算入口唯一（订阅 building 事件后拉取）。

## 二、Step 2 · 架构决策

### 2.1 模块边界：新建 `modules/population.ts`（唯一 owner）

独占 `population` 集合。状态结构（落地时定稿）：

```ts
interface WoundEntry {
  count: number;   // 这批伤兵的人口数
  healAt: number;  // 治愈时刻(ms)，Scheduler 触发
  taskId: string;  // Scheduler 句柄（resume 重登记）
}

interface LaborBuilding {   // 从 building.GetLaborContext 拉来的快照，只读缓存
  kind: string;             // main/barracks/stable/workshop/academy/smithy/woodcutter/...
  level: number;
  resource?: string;        // 仅资源田：wood/clay/iron/crop
}

interface PopulationState {
  villageId: string;
  currentPop: number;
  woundedPool: WoundEntry[];
  lastTick: number;              // 惰性结算基准
  prosperity: number;            // building 算好的繁荣度快照
  laborBuildings: LaborBuilding[]; // building 劳动力上下文快照
}
```

- **初始化**：新村创建时 `currentPop = 软上限(初始粮食上下文)`（新村开局满员，设计 B-1）。故 population.createVillage 必须在 economy/building.createVillage **之后**（此时 economy 已有正确 baseRate/upkeep）。

### 2.2 派生全部在 Population 内部算，对外只给快照（铁律#4）

给定当前 `P=currentPop`、缓存的 `laborBuildings`、config 常量：

- **繁荣度增长率**：`growthPerHour = prosperity × pop_growth_per_prosperity`。
- **单建筑饱和阈值** `S_b(L)`：资源田 `laborSaturation × prodGrowth^(L-1)`；其余 `laborSaturation × L`（设计 H-①）。
- **速率类劳动倍率**：`rate_mult_b = pop_labor_floor + laborBonusMax_b × min(1, P/S_b(L))`。
- **建造时间倍率**（城镇中心）：`time_mult = 1 − laborBonusMax_main × min(1, P/S_main(L))`。
- **资源田聚合产率修正器**（喂给 economy）：economy 存的是**同类资源田原始总产率** `baseRate[t]`（building 上报，未含劳动）。population 按各田实例算**加权平均倍率**：
  `effMult[t] = Σ_i F0(L_i)·rate_mult_i / Σ_i F0(L_i)`（`F0(L)=prodBase·prodGrowth^(L-1)`）。
  于是 `economy 毛产率 = baseRate[t] × effMult[t]` 精确等于逐田加权求和，无近似。传给 economy 的修正量 `mult[t] = effMult[t] − 1`（范围约 −0.25..0）。
  > 单资源田（如罗马开局只有 1 块 cropland）时加权平均退化为该田倍率，与设计 §4.2 收敛演算一致。
- **软上限 L**：`L = (baseCropPerHour × effMult[crop] − buildingUpkeep − troopUpkeep) / pop_per_capita_crop`，其中三项来自 `economy.GetCropContext`（`buildingUpkeep/troopUpkeep` **不含** civilian_pop）。
- **充裕比** `λ = min(1, P / max(1, L))`；**治疗时长** `= pop_heal_time / (1 + pop_heal_bonus × λ)`。

### 2.3 惰性结算模型（增长 / 超限减员 / 伤兵到期）

沿用 economy 同款「读写前按 Δt 补算」：

```
settle(now):
  Δt = (now - lastTick)/3600s
  读 economy.GetCropContext → 算 L、netCrop
  若 P < L:  P += min(growthPerHour × Δt, L - P)      // 增长不越过软上限
  若 P > L 且 currentCrop <= 0:                        // 粮仓见底才减员（缓冲）
      减员速率随净粮赤字放大：deathRate = (P - L) × pop_death_rate_factor
      P -= min(deathRate × Δt, P - L)
  // 伤兵到期由 Scheduler 独立触发，不在 settle 内轮询
  lastTick = now
  重算派生 → 若 civilian_pop 粮耗或 effMult 变化超阈值:
      economy.SetUpkeep(civilian_pop) + economy.SetRateModifier(pop_labor)
  emit population.Changed（供 gateway 推送）
```

- **减员触发口径（决策 C1 收口）**：population **不自己判断粮仓何时空**，而是订阅既有 `economy.CropDeficit`（粮仓触底且净粮为负时 economy 已发，military 逃兵也用它）。收到后 population `settle` 会看到 `currentCrop<=0` 从而进入减员分支；同时 population 向 Scheduler 注册一个「持续减员再结算」的粗粒度任务，直到 `P<=L` 或净粮转正。这样减员既真实（粮仓由 economy 真实扣减）又不需要 population 轮询。
- **`pop_death_rate_factor`**：把「净粮赤字→减员速率」的比例常量（设计正文以文字描述"负得越多减越快"，此处显式化为一个常量，列入 §四待补）。

### 2.4 【重点】economy ↔ population 无循环解耦的数据流

**表面上的环**：`P ↑ → 农田劳动比 ↑ → 粮食产率 ↑ → 软上限 L ↑ → P 有空间继续 ↑`。设计 §4.2 已用数学证明其收敛（环路增益 0.25，几何收敛）。**架构上我们把它拆成无环调用图**——靠「单向写 + 惰性只读快照 + 离散推送」，任何一次调用都不回调发起方：

```
                 (事件, 松耦合)
 building.Built/Upgraded ───────────────▶ population.on(...)
                                              │  拉取(只读,无回调)
                                              ▼
                                   building.GetLaborContext ──▶ {prosperity, buildings[]}
                                              │ 缓存 laborBuildings/prosperity
                                              ▼
                                      population.settle(now)
                            ┌───────────── 读(只读,无回调) ──────────────┐
                            ▼                                            │
                 economy.GetCropContext ──▶ {baseCropPerHour(原始,未含劳动),
                            │                 buildingUpkeep, troopUpkeep,
                            │                 currentCrop, cropCapacity}
                            │  用它 + 自算 effMult[crop] 得软上限 L、netCrop
                            ▼
                 ┌─── 写(单向,economy 只存不问) ───┐
                 ▼                                  ▼
   economy.SetUpkeep(civilian_pop=P×c)   economy.SetRateModifier(pop_labor, mult[])
                 │                                  │
                 ▼                                  ▼
        economy 下次 settle 真实扣粮仓        economy 毛产率 = baseRate × (1+mult)
                 │
                 ▼ (粮仓触底且净粮<0)
        economy.CropDeficit 事件 ──────────▶ population.on → 进入减员
```

**为什么无环**（运行时调用图层面）：
1. `economy.GetCropContext` / `building.GetLaborContext` 都是**纯读**，内部绝不 send 回 population，也不 emit 触发 population。→ 读不成环。
2. `economy.SetUpkeep` / `economy.SetRateModifier` 是**单向写**，economy 只把值存下（`cropUpkeep[source]=…`、`rateModifiers` 覆盖），下次它自己 settle 时才用；不回调 population。→ 写不成环。
3. `economy.CropDeficit` 是 economy 自身 settle 时发的**事件**，population 被动订阅；population 处理它时只读/自算，不同步回调 economy 产生新 Deficit。→ 事件不成环。
4. `building.Built/Upgraded` 是 building 自身完工时发的事件；population 处理时只**拉**（GetLaborContext）不**推**回 building。→ 不成环。

**收敛在跨结算的多次离散迭代中自然发生**（§4.2 的 0.25 增益），不是运行时递归——每次 settle 用的是「上一快照的 P/倍率」，本次算完再推新倍率给 economy，下次再读。就是设计文档演算表里那张「迭代逐行收敛」的工程化落地。

> **口径锁定**：`GetCropContext.baseCropPerHour` = economy 的 `baseRate.crop×3600`（**原始**、building 上报、未含劳动）；`buildingUpkeep=cropUpkeep['building']`、`troopUpkeep=cropUpkeep['troops']`，**不含** `civilian_pop`（那是 L 要衡量的容量，不能计进分子）。economy 实际扣粮时对 crop 应用的 `effMult` 与 population 算 L 用的是**同一个** `SetRateModifier` 值 → 满员时净粮≈0 自洽（决策 C1）。

### 2.5 劳动力增幅注入五条速率轴

| 轴 | 注入点 | 取值方式 |
|----|--------|---------|
| 资源产率 | economy 产率派生管线 | population 推 `economy.SetRateModifier(pop_labor, mult[wood..crop])`（加权平均倍率−1） |
| 建造速度 | building.buildTime | building 在 build/upgrade 时 `send population.GetLaborMult('main')`，把 `time_mult` 乘进现有 `buildTime` |
| 练兵速率 | military.trainTroops | military 起训时 `send population.GetLaborMult(def.building)`，`trainSec_eff = trainSec / rate_mult` |
| 锻造速率 | military.upgradeSmithy | 同上，`GetLaborMult('smithy')`，调锻造耗时（当前锻造是瞬时扣费，若二期改为有时长再乘） |
| 研究速率 | **academy（暂无模块）** | 预留：academy 建成后起研究时 `GetLaborMult('academy')`。本次**不实现**，仅在文档标注钩子 |

> **命令 vs 事件的取舍**：资源产率用**命令**（`SetRateModifier`）而非事件，与 building→economy 现有 `SetBaseRate/SetCapacity/SetUpkeep` 的「上报式命令」风格一致，economy 无需订阅新事件。其余四轴是**读时按需拉**（`GetLaborMult`），因为它们只在"起某个动作那一刻"取一次快照。`population.LaborSnapshotUpdated` 事件仅作为可选广播（notifications/UI 感知）保留，核心链路不依赖它。

### 2.6 特殊单位与伤兵/返还的归属层

| 情形 | 处理层 | 说明 |
|------|--------|------|
| 拓荒者 popCost | 训练时 `ConsumePop` 扣、**永不返还** | units.csv 加 `popPermanent=1`；population 在 `AddWounded`/`ReturnPop` 里跳过 popPermanent 单位 |
| 首领/元老 | 与普通兵同：死走伤兵、解散返还 | `popPermanent=0` |
| 伤兵转化比例 | **population** 用 config 算 | combat 只传原始 `losses`；`wounded=Σ floor(count×popCost×pop_death_recovery_ratio)`（跳过 popPermanent） |
| 永久阵亡 | 隐式 | `losses×popCost − wounded`，不进任何池 |
| 出征中军队 | 不在城内、不可解散 | 归 movement 管辖；解散只作用于驻村兵（military.DisbandTroops 只减 `troops`） |

### 2.7 配置优先

新增数值/兵种 popCost/建筑劳动参数**只改 CSV**。劳动饱和/增幅下沉到 `buildings.csv` 三列（设计已定），常量入 `game_constants.csv`。

## 三、Step 3 · API 契约

### 3.1 服务器 ↔ 客户端（Request / Response / Push）

**Population MANIFEST（新模块）：**

| Action | 内部 Command | ownVillage/auth | Response payload |
|--------|-------------|-----------------|------------------|
| `GetPopulation` | `population.GetSnapshot` | ✓/✓ | 见 A |

**Military MANIFEST 增行：**

| Action | 内部 Command | ownVillage/auth | Response |
|--------|-------------|-----------------|----------|
| `DisbandTroops` | `military.DisbandTroops` | ✓/✓ | `{ troops, returnedPop }` |

**A. `GetPopulation` 响应（人口面板快照，派生全给结果）：**
```ts
{
  currentPop: number,
  softLimit: number,
  growthPerHour: number,        // 客户端本地外插用
  lambdaRatio: number,          // 充裕比，UI 展示
  wounded: { total: number, entries: Array<{ count, healAt }> },
  laborMults: {                 // 各轴当前倍率(0..1 或 建造 time_mult)，UI 展示百分比
    production: { wood, clay, iron, crop },  // effMult
    build: number,               // time_mult(main)
    train: { barracks, stable, workshop },
    smithy: number,
    // academy: number           // 预留，暂缺
  },
  lastTick: number,
}
```

**Push（eventPushMap）：**
| 内部事件 | 对外推送 | 触发 |
|----------|---------|------|
| `population.Changed` | `PopulationChanged` | settle 后 pop/softLimit/wounded 变化；训练扣人、伤兵登记、治愈、减员 |

> payload：`{ villageId, currentPop, softLimit, growthPerHour, lambdaRatio, woundedTotal }`。gateway 按 villageId 定向推送（现有机制）。
> 派生只给快照：Response/Push 不下发饱和公式/常量，只给算好的 mult/limit（铁律#4）。

### 3.2 模块 ↔ 模块（Command / Event）

**Population 注册的 Command（他人调用）：**

| Command | 调用方 | payload | 成功 | 失败 |
|---------|--------|---------|------|------|
| `population.GetSnapshot` | gateway | `{villageId}` | 见 3.1-A | `village_not_found` |
| `population.GetLaborMult` | military, building | `{villageId, buildingKind}` | `{mult:number}` | — |
| `population.ConsumePop` | military | `{villageId, unit, count}` | `{ok, consumed}` | `insufficient_population` |
| `population.ReturnPop` | military | `{villageId, units:Record<code,count>}` | `{ok, returned}` | — |
| `population.AddWounded` | combat | `{villageId, losses:Record<code,count>}` | `{ok, wounded, permanentDead}` | — |

> `ConsumePop` 传 `unit,count`（population 用 config 查 popCost，含 popPermanent 判定）。`ReturnPop`/`AddWounded` 传兵种损失映射，population 统一用 config 换算并跳过 popPermanent。`CheckTrainable`（只读预检）可用 `GetSnapshot` 现算，暂不单列命令。

**Population 发出的 Event：**

| Event | 时机 | payload | 谁关心 |
|-------|------|---------|-------|
| `population.Changed` | 结算后关键量变化 | `{villageId, currentPop, softLimit, growthPerHour, lambdaRatio, woundedTotal}` | gateway（推送）、notifications（可选） |
| `population.LaborSnapshotUpdated` | 劳动倍率快照更新（可选） | `{villageId, laborMults}` | 广播/UI（核心链路不依赖，见 §二·2.5） |

**Population 订阅的 Event：**

| Event | 来源 | 用途 |
|-------|------|------|
| `building.Built` / `building.Upgraded` | building | 拉 `GetLaborContext` 重算繁荣度+劳动力 |
| `economy.CropDeficit` | economy | 粮仓触底 → 触发/持续减员结算 |

**Economy 新增 Command：**

| Command | 调用方 | payload | 返回 |
|---------|--------|---------|------|
| `economy.SetRateModifier` | population | `{villageId, source:string, mult:Partial<ResMap>}` | `{ok}` |
| `economy.GetCropContext` | population | `{villageId}` | `{baseCropPerHour, buildingUpkeepPerHour, troopUpkeepPerHour, currentCrop, cropCapacity}` |

**Building 新增 Command：**

| Command | 调用方 | payload | 返回 |
|---------|--------|---------|------|
| `building.GetLaborContext` | population | `{villageId}` | `{prosperity, buildings:Array<{kind,level,resource?}>}` |

> `GetLaborContext` 只回 `laborAmplified=1` 的实例（含 main、各资源田、军事/学院/铁匠建筑）；prosperity=`Σ level×prosperityPerLevel`（building 计算，铁律#4）。

**命名规范核对**：命令祈使式（`population.ConsumePop`/`economy.SetRateModifier`/`building.GetLaborContext`）、事件过去式（`population.Changed`/`building.Built`），均带模块命名空间。✓

### 3.3 建筑维护 source 改名（收口）

`building.reportPopulation()`：`economy.SetUpkeep{source:'population'}` → `{source:'building'}`。同步：economy `GetCropContext` 读 `cropUpkeep['building']` 作为 buildingUpkeep。（`cropUpkeep` 以 source 字符串为键，改名无结构风险，但需一次性全量替换。）

## 六、持久化与刷档

- **持久化**：`population` 集合与其它进度集合同构（`store.set('population', villageId, state)`），随 JsonFileStore 落盘。伤兵 `taskId` 不持久化其调度，靠 `resume()` 依 `healAt` 重登记（与 building/military 同模式）。
- **刷档必要性**：新增 `population` 集合 + economy 收支口径变化（新增 civilian_pop 真实扣粮）+ building upkeep source 改名。旧存档无 population 文档且未登记 civilian_pop。
  - 本地/测试：`npm run reset:season`（`rebuildVillages` 重跑 `doCreateVillage` → 建 population、满员开局）。
  - 部署：按 CLAUDE.md「数据结构变更（新集合）必须带刷档」→ `bash .claude/deploy/deploy.sh --reset respawn`。坐标不变，`season` 亦可；遵项目约定用 `respawn`，二者都会重跑 createVillage 建 population。

## 七、shared 类型

- Push 是「字符串事件名 + 自由 payload」，`PopulationChanged` **多半无需**新增 wire 类型。若前端团队希望强类型面板结构，可在 `packages/shared` 加一个 `PopulationSnapshot` 接口供前后端共享，则需 `npm run build:shared`。默认按「无需改 shared」推进，确有共享需求再补（T0.4 决策点）。
