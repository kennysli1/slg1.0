# 13 · 人口系统设计（硬上限模型 · 繁荣度五轴统一 · 战死即时回收）

> 状态：**v3 完成（2026-08-08）**。`population.ts` v3：人口硬上限由建筑提供（`hardCap = Σ popCapPerLevel × level`）、`availableLabor = hardCap − soldierPop` 为增长目标与拓荒门槛（兼容别名 `softLimit`）、繁荣度加成统一驱动五轴劳动力倍率 `prosperityMult ∈ [0.75,1.0]`、战死经 `RecoverCasualties` 由医院按等级**即时回收**（无伤兵池/无定时器）、粮荒期间停止增长只减员（保士兵逃兵）。测试覆盖：`population.test.ts` / `population-v2.test.ts`（C1–C11）/ `population-regression.test.ts` / `concurrency.test.ts` / `multiplayer-pvp.test.ts` / `found-village.test.ts`，服务端 186 项、客户端 40 项全通。
> 本文是「人口系统」的唯一设计入口，涵盖机制 A–H、完整数值表、演算示例与模块边界。

> **后续增量（v3 定稿后）**：人口增长绑定城镇中心（移除 `pop_growth_per_hour`）、繁荣度改为平民占总人口比例驱动（移除 `pop_race_labor_min_*`）、新增金币经济（人口税 + 逐等级 `costGold`）与 30s 周期结算（修复金币显示 +X/时却不涨）。详见 §七。
> 数值均基于 `config/buildings.csv`（`popCapPerLevel` 列）、`config/units.csv`、`config/game_constants.csv` 现有参数推导，不凭空捏造量级。

## 一、设计目标

**一句话定位**：人口是城市的「文明活力」——它不仅是兵力池，更是驱动经济、研究、练兵、锻造和建设的综合生命力指标。损失人口会同时拖慢**资源产出/研究/练兵/锻造/建造**五条速率轴，从而给战争行为真实定价。

**两条核心关系**：

| 关系 | 机制 | 直觉 |
|------|------|------|
| **硬上限** | 建筑等级之和决定人口上限（`hardCap = Σ popCapPerLevel × level`） | "城市越大，能养活的人越多" |
| **繁荣度加成** | 劳动人口占比越高 → 繁荣度加成越高 → 五轴速率倍率越高 | "人尽其用，城市越有活力" |

**粮食的作用**：粮食不再决定人口上限（v2 的「软上限」已废弃），而是作为**真实口粮消耗**登记进 economy：
- 平民：`currentPop × popCropPerLabor`（默认口粮，每人 1/h）
- 士兵：`popCost × (popCropPerLabor + upkeep)` —— **既吃与平民同源的默认口粮（每人 1/h），再叠加兵种军晌 upkeep**。即「每个兵默认 1 耗粮 + 1 军晌耗粮」（popCost=1 的标准兵）。
- 训练一个兵：释放平民口粮 `popCost×popCropPerLabor`，增加士兵口粮 `popCost×(popCropPerLabor+upkeep)`，净变化 `popCost×upkeep ≥ 0`（始终不降）。

粮食净产率为负且存量耗尽 → 进入**粮荒状态机**（停止增长、平民减员、士兵逃兵）。

**判断标准（核心原则）**：
> 人口 = 人手/劳动力。它加速的是"靠人做的、有速率的过程"（速率类），改变不了"靠材料/等级堆出来的静态属性"（存量/物理类）。

| 速率类（吃人口） | 存量/物理类（不吃人口） |
|----------------|----------------------|
| 资源产出速率、研究速率、练兵速率、锻造速率、建造速度 | 仓库/粮仓容量、城墙防御值/耐久、集结点集结容量 |

**设计原则**：
- 人口用**隐式影响**（自动调节）而非显式劳动力分配拨杆，与 SLG 异步放置节奏匹配。
- UI 明确展示人口数、硬上限、可用劳动力、各项速率加成百分比，让玩家理解系统而不会困惑。
- 唯一一类隐式作用：**繁荣度五轴劳动力增幅**（`prosperityMult` 统一作用于五个速率轴），构成「人口=文明活力」整体感知。

## 二、核心机制（A–H）

### A. 繁荣度与劳动力加成（Prosperity → prosperityMult）

```
硬上限   hardCap       = Σ( 建筑 level × popCapPerLevel )      // 对城内所有已建建筑求和
士兵人口 soldierPop    = garrisonPopCost + enRoutePopCost       // 由 military 上报
可用劳动力 availableLabor = hardCap − soldierPop               // 增长目标 / 拓荒门槛 / softLimit 别名
平民占比 civilFrac    = currentPop / (currentPop + soldierPop) // 平民占总人口比例 ∈[0,1]
繁荣度加成 prosperityBonus = clamp( civilFrac / pop_prosperity_full_ratio, 0, 1 ) × overcrowd
              // overcrowd：人口超过硬上限时的拥挤惩罚（见下），正常稳态=1
五轴倍率 prosperityMult  = pop_labor_floor + (1 − pop_labor_floor) × prosperityBonus   // ∈ [0.75, 1.0]
```

- `prosperityBonus`：由**平民占总人口比例** `civilFrac` 驱动——`civilFrac ∈ [0,1]`，达到 `pop_prosperity_full_ratio`（默认 0.70，即 ≥70% 平民）为满值，低于则线性降到 0；再乘 `overcrowd` 拥挤惩罚（人口超出硬上限时按 `pop_overcap_penalty_full_ratio` 在 1→2 倍间线性降到 0，正常稳态不触发）。
- `prosperityMult`：全城唯一劳动力倍率，**五条速率轴共用同一个值**（production / build / train / research / smithy），范围 `[pop_labor_floor, 1.0]`（默认 `[0.75, 1.0]`）。满员时 = 1.0，劳动力枯竭时 = 0.75（防死亡螺旋）。
- **与硬上限解耦**：繁荣度不再由 `currentPop / hardCap`（劳动占比）计算，而由平民占总人口（平民+士兵）比例计算；建造/升级改变 hardCap 不再造成繁荣度负收益。

> 例：罗马新村 currentPop=64、soldierPop=0 → `civilFrac=64/64=1.0` → `prosperityBonus = clamp(1.0/0.70,0,1)=1.0` → `prosperityMult=1.0`。
> 若战后 currentPop 跌到 10、soldierPop=90（civilFrac=0.10）→ `prosperityBonus = clamp(0.10/0.70,0,1)=0.14` → `prosperityMult≈0.785`（五轴被压低）。
> **注**：旧版 `pop_race_labor_min_{tribe}`（种族下限）已移除。部族差异现仅体现于**最大动员比例** `pop_race_mobilize_max_*`（士兵占总人口上限：罗马0.75/高卢0.70/条顿0.80），用于限制征兵而非繁荣度（见 §3.1 / §7.2）。

### B. 人口增长与硬上限

#### B-1. 硬上限（由建筑提供）

```
hardCap = Σ( 建筑.level × 建筑.popCapPerLevel )
```

- 每栋建筑在 `buildings.csv` 的 `popCapPerLevel` 列给出每级贡献（见 §3.2）。
- `building.Built` / `building.Upgraded` 事件触发 `population` 重算 `hardCap` 并 emit `population.Changed{event:'capChanged'}`。
- **人口硬上限与粮食解耦**：粮食只影响"能不能养活"（粮荒减员），不影响 `hardCap` 本身。

#### B-2. 可用劳动力（增长目标 / 拓荒门槛）

```
availableLabor = hardCap − soldierPop
softLimit     = availableLabor        // 兼容别名（movement 拓荒门槛仍读 softLimit）
```

- 平民人口 `currentPop` 只朝 `availableLabor` 增长，**永不越过**它（守恒：`currentPop + soldierPop ≤ hardCap`）。
- 拓荒（建新城）门槛读 `softLimit`：发起拓荒需 `availableLabor ≥ found_min_soft_limit`（默认 350，CSV 可被 `found_min_soft_limit` 覆盖为 200）。

#### B-3. 增长公式

```
growthPerHour = main.popGrowthPerLevel × mainLevel     // 速率上限（绑定城镇中心，GM 可调）
gap           = availableLabor − currentPop            // 增长空间
本帧增长       = min( gap , growthPerHour × dtHours )  // 朝 availableLabor 收敛，不超缺口
currentPop   = min( availableLabor , currentPop + 本帧增长 )
```

- 增长只受 `main.popGrowthPerLevel × mainLevel` 缩放（城镇中心每级人口增速：CSV `buildings.main.popGrowthPerLevel`，GM 面板可调），与繁荣度无关（繁荣度通过五轴速率间接体现"活力"，但人口基数增长由主城等级决定）。
- **粮荒期间（`inFamine`）不增长**：否则减员会与增长相互抵消，人口卡在平衡点无法归零（v3 修复的设计缺陷）。
- **新村开局人口 = 城镇中心 popCap 贡献**：`createVillage` 直接设 `currentPop = 城镇中心当前等级贡献的 popCap 之和（mainPopCap）`，其余默认建筑只贡献 hardCap 不贡献初始人口；人口随后按增速缓慢增长至可用劳动力上限；开局即满员时 `gap=0` → 增长速率为 0（这是正确行为）。

### C. 造兵消耗人口

- 训练开始时**一次性扣除** `数量 × 兵种.popCost` 的平民人口（`ConsumePop`）。
- 若 `currentPop < 所需消耗`，训练被拒绝，返回错误 `insufficient_population`。
- 被扣除的人口进入「士兵形态」——活着的士兵不归还人口，主动解散才归还（见 E）。`soldierPop` 由 military 通过 `SetGarrisonPop` / `SetEnRoutePop` 上报，从而 `availableLabor` 实时下降。
- 军队战死则走即时回收机制（见 D），不是直接归还人口。

---

### D. 战死即时回收（无伤兵池 / 无定时器）

**触发**：战斗结束，某方损失 N 名士兵时，combat 向双方各自村庄发 `population.RecoverCasualties` Command。

```
recoveryRatio = min( pop_hospital_recovery_max,
                     pop_hospital_recovery_base + hospitalLevel × pop_hospital_recovery_per_level )
recovered      = floor( deadPop × recoveryRatio )      // deadPop = 损失数 × unit.popCost
permanentDead  = deadPop − recovered                  // 永久消失
currentPop    += recovered                            // 即时回填，无定时器/无伤兵队列
```

- **v3 取消伤兵池（`woundedPool`）与治愈定时器**：回收在命令内同步完成，`recoverCasualties` 返回 `{recovered, permanentDead}`，并 emit `population.Changed{event:'recovered'}`。
- 回收的人口直接加回 `currentPop`（受 `hardCap` 上限约束；实战中士兵死亡已使 `soldierPop` 下降、腾出 `availableLabor`，故不会越界）。
- 医院等级越高回收比例越高（L0=0.20 → L6 达上限 0.80）。拓荒者等 `popPermanent=true` 单位死亡不回收（人随拓荒者走了）。
- **双方各结算**：攻守双方各自向自己的城市发 `RecoverCasualties`，伤兵回各自城市。

---

### E. 主动解散军队

- 驻守在城内的军队可主动解散：`currentPop += 解散数量 × unit.popCost`，100% 归还人口；**资源不返还**。
- **出征中的军队不能解散**（在途部队由 movement 模块管辖，不在城内）。

---

### F. 特殊单位的人口处理

| 单位类型 | 人口规则 |
|---------|---------|
| **拓荒者** | 训练消耗 `popCost=5`；派出后**永久消耗**，人口不返还（人随拓荒者去建新村了）。`RecoverCasualties` 对 `popPermanent` 单位不回收 |
| **首领/元老**（senator/chief） | 与普通士兵相同：战斗死亡走即时回收，主动解散归还人口 |

---

### G. 建筑被摧毁后的人口响应

攻城锤/投石机破坏建筑 → 该建筑 `popCapPerLevel × level` 贡献消失 → `hardCap` 下降：

| 效果链 | 说明 |
|--------|------|
| `hardCap` 下降 | `availableLabor = hardCap − soldierPop` 随之下降；若 `currentPop > availableLabor`，增长暂停，人口自然被"天花板"压低（下一次减员/不增长即体现） |
| 繁荣度下降（若有） | 五轴 `prosperityMult` 下降 → 各速率变慢 |
| 回落方式 | 非瞬间崩塌：硬上限是"硬墙"，`currentPop` 不会因 `hardCap` 下降而被主动削减，但失去增长空间且后续减员使其缓慢下行 |

---

### H. 人口的唯一隐式作用（五轴繁荣度增幅）

人口通过 `prosperityMult` 这一个统一倍率自动影响五条速率轴，无需手动分配劳动力。UI 应明确展示 `prosperityMult` 与各轴加成数字。

```
prosperityMult ∈ [pop_labor_floor, 1.0]   // 五轴共用同一个值
rate_mult_axis = prosperityMult            // production / build / train / research / smithy 均取此值
```

**五轴映射**：

| 轴 | 受影响的操作 | 倍率来源 |
|----|------------|---------|
| production | 资源田产出 | `prosperityMult` |
| build | 建筑升级耗时 | `prosperityMult`（耗时 ÷ mult） |
| train | 练兵耗时 | `prosperityMult`（耗时 ÷ mult） |
| research | 学院研究耗时 | `prosperityMult`（耗时 ÷ mult） |
| smithy | 铁匠铺升级耗时 | `prosperityMult`（耗时 ÷ mult） |

> 建造/练兵/研究/锻造的"耗时"统一除以 `prosperityMult`：满员时耗时最短，劳动力枯竭时耗时最长（×1/0.75≈1.33）。

**铁匠升级耗时化（v3 新增）**：铁匠铺锻造升级改为**耗时操作**，基础 `smithy_upgrade_sec`，实际耗时 = `smithy_upgrade_sec ÷ prosperityMult`，受繁荣度加速。

#### 两类作用的协同感知

```
人口下降（劳动占比 ↓）
  └→ prosperityMult ↓（地板 0.75）
       ├→ 资源产率 ÷mult 变慢（最多 +33% 耗时）
       ├→ 研究速率变慢（最多 +33% 耗时）
       ├→ 练兵速率变慢（最多 +33% 耗时）
       ├→ 锻造速率变慢（最多 +33% 耗时）
       └→ 建造加速消失（最多 +33% 耗时）
```

战争造成士兵死亡 → 回收仅部分、永久损失其余 → `currentPop` 下降 → `prosperityMult` 下降 → 上述全部路径同时恶化 → 战争有真实代价。

## 四、数值演算示例

> 所有数值基于真实配置：`start_resources=750`、`buildings.main.popGrowthPerLevel=3`（× mainLevel）、`pop_crop_per_labor=1.0`、`pop_labor_floor=0.75`、`pop_prosperity_full_ratio=0.70`、各部族最大动员比例 `pop_race_mobilize_max_*` 见 §3.1。

### 4.1 硬上限与可用劳动力

| 阶段 | 建筑组合（示例） | hardCap | 驻军 soldierPop | availableLabor |
|------|----------------|---------|-----------------|----------------|
| 新村 | main L1 + 6×L1 | ≈64 | 0 | ≈64（满员） |
| 早期 | 10 栋均 L3 | ≈ (20+9×8)×3 ≈ 276 | 训练 20 兵(=20) | ≈256 |
| 中期 | 10 栋均 L8 | ≈ (20+9×8)×8 ≈ 736 | 2000 步兵(=2000) | ≈736（兵多则 availableLabor 被吃满，甚至为负→增长停止） |
| 晚期 | 12 栋均 L15 | ≈ (20+10×8)×15 ≈ 1500 | 5000 混合(=约 8000) | <0（驻军远超硬上限，平民被挤压至 0） |

> **重要**：当 `soldierPop > hardCap` 时 `availableLabor < 0`，`currentPop` 被压向 0（平民被"挤没"）。这是 v3 的硬约束——人口上限是平民+士兵的总容量，暴兵会牺牲平民经济活力。

### 4.2 繁荣度加成与五轴倍率

以罗马为例，`prosperityBonus = clamp(civilFrac / pop_prosperity_full_ratio, 0, 1) × overcrowd`（默认 `pop_prosperity_full_ratio=0.70`，`pop_labor_floor=0.75`），`prosperityMult = 0.75 + 0.25×bonus`。其中 `civilFrac = currentPop / (currentPop + soldierPop)`（平民占总人口比例，分母含士兵）：

| civilFrac (currentPop/(currentPop+soldierPop)) | prosperityBonus | prosperityMult | 五轴耗时倍数 |
|--------------------------------|-----------------|----------------|-------------|
| 1.00（纯平民，无驻军） | 1.0 | **1.00** | ×1.00（最快） |
| 0.70 | 1.0 | **1.00** | ×1.00 |
| 0.425（中点） | 0.61 | **0.90** | ×1.11（+11%） |
| 0.10（重兵压境） | 0.14 | **0.785** | ×1.27 |
| 0.0（零人口） | 0.0 | **0.750** | ×1.33（+33%，地板） |

> 注：`civilFrac` 分母含士兵，故「暴兵」会同时压低繁荣度（士兵越多平民占比越低）。`overcrowd` 仅在 `currentPop > hardCap` 瞬态时 <1，正常稳态 = 1。

铁匠升级示例（base 30s）：满员 30s；半员（mult 0.875）≈34s；零人口（mult 0.75）40s。

### 4.3 增长收敛示例

新村满员（开局 `currentPop = 城镇中心 popCap 贡献`，`gap=0`）→ 增长速率 = 0。制造增长空间（如 `ConsumePop(20)` 或训练后 soldierPop 不变而 currentPop 被扣）→ `gap=20`、`main.popGrowthPerLevel×mainLevel = 3×1 = 3/hr`（CSV 默认 3，GM 可调）：

| 经过时间 | currentPop | 说明 |
|---------|-----------|------|
| 0 | 44（=64−20） | 消耗后 |
| 1h | 64（=min(64, 44+20)） | 1 小时内补满 availableLabor |

若 `mainLevel=5`，增长上限 = 15/hr（= 3×5），补满更快。增长**永不越过 availableLabor**。

### 4.4 战死即时回收示例

**场景**：中期村庄，均衡人口 736，拥有 2000 名罗马步兵（popCost=1）。战斗损失 500 步兵，医院 L0（recoveryRatio=0.20）：

```
recovered     = floor(500 × 1 × 0.20) = 100   → 即时加回 currentPop
permanentDead = 500 − 100             = 400   → 彻底消失
```

- 战斗同时使 military 把 garrisonPopCost 由 2000 降到 1500 → `availableLabor` 由 −1264 升到 −764（仍为负，平民仍被挤）。
- `currentPop` 立即 +100（若未被 hardCap 夹住）：这是 v3 与 v2 伤兵池的本质区别——**没有等待治愈的过程**。
- 实际净损失：400 永久阵亡（即 80% × 500）。对比主动解散（不打仗）：500 pop 100% 归还，0 永久损失。

### 4.5 粮荒减员示例

**触发**：economy 检测 `crop ≤ 0 且 净产率 < 0` → 边沿 emit `economy.CropDeficit` → population 调度首个 `runStarveTick`（每 `pop_famine_tick_sec=300s` 一次）。

```
每 tick 减员 = currentPop × (1 − exp(−pop_death_rate_factor × (tickSec/3600)))
            = currentPop × (1 − exp(−0.5 × 300/3600))
            = currentPop × (1 − exp(−0.0417)) ≈ currentPop × 0.0408   （约 4%/tick）
```

- **粮荒期间不增长**：否则减员与增长抵消，人口卡在平衡点（v3 已修复）。
- 持续赤字 → `currentPop` 逐 tick 指数衰减趋近 0；同时军事模块按 10%/tick 比例**逃兵**（不回补人口）。
- 粮食恢复（净产率转正、存量 >0）→ 下一 tick `computeDeficit` 为 false → emit `population.Changed{event:'recovery'}`，`inFamine=false`，增长恢复。

## 五、影响面与模块边界

### 5.1 新模块 `modules/population.ts`（Owner）

**唯一状态归属**：人口相关数据只由此模块拥有，其他模块不得直接读写其 store 集合。

```typescript
// population.ts 拥有的状态结构（v3）
interface PopulationState {
  villageId: string;
  currentPop: number;        // 平民/劳动人口（不含士兵），朝 availableLabor 增长
  hardCap: number;           // 硬上限（建筑 Σ level×popCapPerLevel），building 事件重算
  mainLevel: number;         // 主城等级（增长速率缩放）
  tribe: string;             // 部族（决定最大动员比例 popRaceMobilizeMax，仅影响征兵上限，不参与繁荣度）
  garrisonPopCost: number;   // 驻守城内士兵总 popCost（military 上报）
  enRoutePopCost: number;    // 出征中士兵总 popCost（military/movement 上报）
  inFamine: boolean;         // 是否处于粮荒状态机
  starveTaskId?: string;     // 当前饥荒 tick 任务 id（undefined=未运行）
  lastTick: number;          // 上次惰性结算时间戳(ms)
}
// 注意：v3 无 woundedPool / wounded 字段
```

**初始化**：`createVillage` 查 `building.GetPopCap` 得 `hardCap + mainLevel`，直接设 `currentPop = hardCap`（满员开局）。

### 5.2 对现有模块的改动

| 模块 | 改动内容 | 铁律检查 |
|------|---------|---------|

#### Events（population.ts 发出）

所有 `population.Changed` 事件统一携带 v3 公共字段：

```typescript
  event: 'consumed' | 'returned' | 'recovered' | 'famine' | 'starved' | 'recovery' | 'capChanged';

```

| Event | 时机 | 专属字段 |
|-------|------|---------|
| `population.Changed{event:'consumed'}` | ConsumePop | `consumed` |
| `population.Changed{event:'returned'}` | ReturnPop | `returned` |
| `population.Changed{event:'recovered'}` | RecoverCasualties | `recovered, permanentDead` |

| `population.Changed{event:'starved'}` | 粮荒持续 tick | `reduced` |

| `population.Changed{event:'capChanged'}` | 建筑变化重算 hardCap | — |

> **v3 无 `wounded` / `woundedPool` / `lambdaRatio` / `cropDeficitRate` / `laborDemand` 等 v2 字段**；`softLimit` 是 `availableLabor` 的别名，仍存在以兼容 movement 拓荒门控。

#### 时间驱动

- **惰性结算**：人口增长/粮荒减员采用 economy 同款惰性结算——读时按 `Δt` 补算，不每 tick 推进。
- **粮荒 tick**：`economy.CropDeficit` 边沿触发，向 Scheduler 注册 `popFamineTickSec` 间隔任务，到时 `runStarveTick`（减员 + 续排/退出），无 setInterval。
- **战死回收**：`recoverCasualties` 同步完成，无定时器（v3 关键简化）。

### 5.4 四条铁律自查

| 铁律 | 遵守情况 |
|------|---------|
| **状态归属唯一** | `currentPop` / `hardCap` / `soldierPop` 只在 `population.ts`；其他模块通过 Command/Event 读写 |
| **跨模块只传 Command/Event** | military → `ConsumePop`/`SetGarrisonPop`/`ReturnPop`；combat → `RecoverCasualties`；economy → `CropDeficit` 事件；movement → 读 `softLimit` 别名；无跨模块直接 import |
| **时间统一走 Scheduler** | 惰性结算（读时补算）+ 粮荒 tick 走 Scheduler，不用 setInterval/setTimeout |
| **派生属性对外只给快照** | `prosperityMult` / `availableLabor` / `softLimit` 均在内部计算，对外 `GetSnapshot`/`GetLaborMult` 只返回结果值 |

## 六、平衡风险与上线监控指标

### 主要风险点

| 风险 | 描述 | 缓解措施 |
|------|------|---------|
| **死亡螺旋** | pop低→五轴变慢→发展停滞 | `pop_labor_floor=0.75` 保证最低 75% 速率；满员开局提供初始缓冲 |
| **暴兵挤占平民** | soldierPop > hardCap → 平民归零、经济停摆 | 这是预期硬约束；拓荒门槛 `found_min_soft_limit` 防止无兵可派 |
| **练兵速率差距过大** | 满员 vs 零人口耗时差 33% | 上限 33% 刻意设计（战争代价感）；嫌慢可调 `pop_labor_floor`（抬地板）或降低 `pop_prosperity_full_ratio`（更快满繁荣） |
| **战死无惩罚套利** | 反复训练-战死-回收刷兵 | 回收仅部分（医院 L0 仅 20%），其余永久损失；回收不回士兵，仍需重新花资源训练 |
| **拓荒者 pop 阻塞扩张** | 3 拓荒者=15 pop | 新村满员开局，训练后仍有余量 |

### 上线后监控指标

| 指标 | 采样 | 告警阈值 | 调参 |
|------|------|---------|------|
| **平均战后 pop 恢复时间** | 战报 + 快照 | 恢复过快/过慢 | `buildings.main.popGrowthPerLevel`（× mainLevel） |
| **军民比** | `soldierPop / hardCap` | 长期 >1 → 平民被挤没 | 检查部队规模/硬上限 |
| **prosperityMult 均值** | GetSnapshot.prosperityMult | 中期均值 <0.85 → 活力失效 | 上调 `popCapPerLevel` 或下调 `pop_prosperity_full_ratio` |
| **粮荒发生率** | inFamine 翻转日志 | 过高 → 口粮/产出失衡 | `pop_crop_per_labor` / 农田产出 |
| **战死回收利用率** | recovered / 总阵亡 | <10% → 玩家忽视 | 提高 `pop_hospital_recovery_base` |

## 七、后续迭代补遗（人口 / 金币 / 注意事项）

> 本段汇总 v3 设计定稿之后的增量改动与线上踩坑，便于追溯，避免与设计正文（§A–§H）脱节。

### 7.1 人口增长绑定城镇中心（替换 `pop_growth_per_hour`）
- **改动**：旧的全局常数 `pop_growth_per_hour` 已移除。人口增速改为 `growthRateRaw = buildings.main.popGrowthPerLevel × mainLevel`（CSV `buildings.csv` 的 `popGrowthPerLevel` 列，仅城镇中心有意义，其余 0；GM 平衡面板可调）。
- **开局人口**：`createVillage` 直接设 `currentPop = 城镇中心当前等级贡献的 popCap 之和（mainPopCap）`，其余默认建筑只贡献 hardCap 不贡献初始人口；人口随后按增速缓慢增长至可用劳动力上限。
- **含义**：人口增速与主城等级挂钩，升级主城同时加快人口恢复与金币税基。

### 7.2 繁荣度模型重写（civilian-fraction，移除 `pop_race_labor_min_*`）
- **改动**：繁荣度不再由 `currentPop / hardCap`（劳动占比 vs 种族下限 `raceMin`）计算，改为由**平民占总人口比例** `civilFrac = currentPop / (currentPop + soldierPop)` 驱动（≥ `pop_prosperity_full_ratio` 满值，线性降到 0），并新增 `pop_overcap_penalty_full_ratio`（人口超硬上限拥挤惩罚）。
- 部族差异保留，但仅用于**最大动员比例** `pop_race_mobilize_max_*`（士兵/总人口上限，罗马0.75/高卢0.70/条顿0.80），用于限制征兵（`mobilize_cap_exceeded`），不再参与繁荣度。
- **好处**：建造/升级改变 hardCap 不再造成繁荣度负收益（v3 设计时的痛点）。

### 7.3 金币经济（Gold Economy）
- **唯一来源**：人口税。`settle()` 中 `goldGained = currentPop × gold_tax_per_civilian_per_hour × dtHours`，单向 `economy.Grant{gold}`，绑定城镇中心、与人口增速同节奏、**不受繁荣度影响**、无上限（`GOLD_CAP = Number.MAX_SAFE_INTEGER`）。
- **唯一自然消耗**：建造/升级的逐等级金币成本 `costGold`（`building_levels.csv` 列，默认 1，GM 可调）；用途为雇佣兵（`mercenarycamp`）。
- **显示**：快照 `goldPerHour = currentPop × gold_tax_per_civilian_per_hour`（资源条金币速率）。
- **注意事项**：
  1. 金币按 Δt 累加（惰性结算 + 周期 tick），旧版仅靠客户端轮询触发——离线/未开面板时曾出现"显示 +X/时却不涨"，已通过周期结算修复（见 7.4）。
  2. 旧存档 `gold` 为 `null`（NaN 序列化的历史脏值）或 `baseRate` 缺 `gold` 键时，`settle()` 自愈为 `start_gold_amount`（=100）/`baseRate.gold=0`，不会卡死。
  3. 平衡覆盖层（`/gm/balance` 写 `data/balance_overrides.json`）中的金币相关项（如 `gold_tax_per_civilian_per_hour`、`buildings.1.popGrowthPerLevel`、`building_levels.*.costGold`）**跨部署/wipe 长期生效**。

### 7.4 周期结算 tick 与金币自愈（线上踩坑修复）
- **问题**：金币显示 `+2100/h` 但余额不增。根因为早期一个 `NaN`（修正 GM 覆盖键错位 bug 前 `gold_tax` 未生效、或旧村庄 `baseRate` 缺 `gold` 键）经 JSON 序列化成 `null`，原迁移兜底只处理 `undefined`，导致 `economy.Grant` 累加 `null+数=NaN`→再写回 `null`，永久卡死。
- **修复**：
  - `economy.settle()` 迁移块扩展为同时自愈 `resources/capacity/baseRate` 的 `undefined || null || !Number.isFinite`；`grant/grossRate/settle` 循环均加有限性保护。
  - 新增 `population` 周期结算（`scheduleSettleAll`，每 30s 一次）+ 客户端 `GetPopulation` 轮询双触发，保证人口与金币**离线也持续累加**。
- **验证**：服务端测试 `population-regression.test.ts` 覆盖 null 自愈、周期 tick 累加、旧村庄 baseRate 缺键自愈三场景；部署后线上金币由 `null → 29.69` 并持续上涨。

### 7.5 平衡调参覆盖层（`/gm/balance`）
- 入口：`/gm` → 「平衡调参」，或直接访问 `/gm/balance`。四类可编表：`buildings`（含 `popGrowthPerLevel`）、`building_levels`（含 `costGold`）、`units`、`constants`（含 `gold_tax_per_civilian_per_hour`）。
- 保存为**覆盖层** `data/balance_overrides.json`（深合并到 CSV 解析结果之上），原子写入 + `reloadConfig` 热重载；与 CSV 同源校验。
- **持久性**：该文件在 `data/` 目录（已 gitignore），`git reset --hard`（部署）只清 `config/*.csv`、不碰 `data/`；`wipe:all` 只重置 `game.json`、不删覆盖文件。故 GM 调参**长期生效、跨部署/刷档存活**。
