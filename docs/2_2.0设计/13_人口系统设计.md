## 一、设计目标

**一句话定位**：人口是城市的「文明活力」——它不仅是兵力池，更是驱动经济、研究、练兵、锻造和建设的综合生命力指标。损失人口会同时拖慢**资源产出/研究/练兵/锻造/建造**五条速率轴，从而给战争行为真实定价。

**两条驱动轴**：

| 轴 | 机制 | 直觉 |
|----|------|------|
| **繁荣度轴** | 建筑越多、等级越高 → 繁荣度越高 → 人口增长越快 | "城市越发达，人越多" |
| **粮食轴** | 粮食净产量决定「软上限」 → 超过软上限时人口开始减少 | "养得起多少人由粮食说了算" |

两轴分工：繁荣度管「增得多快」，粮食管「最多活多少」。互相独立，各施影响。

**判断标准（核心原则）**：
> 人口 = 人手/劳动力。它加速的是"靠人做的、有速率的过程"（速率类），
> 改变不了"靠材料/等级堆出来的静态属性"（存量/物理类）。

| 速率类（吃人口） | 存量/物理类（不吃人口） |
|----------------|----------------------|
| 资源产出速率、研究速率、练兵速率、锻造速率、建造速度 | 仓库/粮仓容量、城墙防御值/耐久、集结点集结容量 |

**设计原则**：
- 人口用**隐式影响**（自动调节）而非显式劳动力分配拨杆，与 SLG 异步放置节奏匹配。
- UI 明确展示人口数、软上限、各项速率加成百分比，让玩家理解系统而不会困惑。
- 两类隐式作用：**劳动力增幅**（五类速率）+ **伤兵治疗加速**，共同构成「人口=文明活力」整体感知。

## 二、核心机制（A–H）

### A. 繁荣度（Prosperity）

```
繁荣度 = Σ( 建筑等级 × prosperityPerLevel )   ，对城内所有已建建筑求和
```

- `prosperityPerLevel` 按建筑主题分档（主城/学院/资源田更高，仓储/城墙更低；见 §3.2）。
- 繁荣度是**只读派生值**，由 building 模块在建筑完工/升级时计算并通过 Event 通知。
- **繁荣度只决定人口增长速率，不决定上限**。

> 例：罗马新村（main8+rally3+barracks5+4资源田×6）→ 繁荣度 ≈ 40
> 中期城繁荣度随建筑等级与主题权重上升；实际增速再乘阶段递减 scale

---

### B. 人口增长与粮食软上限

#### B-1. 人口增长

```
增长速率 (pop/hr) = 繁荣度 × pop_growth_per_prosperity
```

- 人口按此速率**持续增长**（与 economy 同款惰性结算，读写时按时间差补算）。
- **没有硬上限**；增长只被粮食的软上限间接制约（见 B-2）。
- **新村开局满员**：新村创建时 `currentPop` 直接设为当前软上限值，无需等待增长。

#### B-2. 粮食软上限

```
软上限 L = ( 粮食产量 × 劳动加成(P) − 建筑维护 − 军队维护 ) ÷ pop_per_capita_crop
```

- **粮食产量**：含劳动力加成后的实际产率（见 H-①，农田适用速率类劳动力模型）。
- **建筑维护**：现有 `sumPop(lv)=lv×(lv+1)/2` 机制（不变，沿用现有 economy 计算）。
- **军队维护**：`Σ(unit.upkeep)`（现有机制，不变）。
- `pop_per_capita_crop`：每人每小时消耗的粮食量（新增常量）。

#### B-3. 人口与软上限的动态关系

| 当前状态 | 行为 |
|----------|------|
| `currentPop < L`（低于软上限） | 人口以 `繁荣度 × 增长系数` 速率持续增长；粮仓有净余流入 |
| `currentPop ≈ L`（接近软上限） | 人口增长被粮食消耗平衡，趋向稳定 |
| `currentPop > L`（超过软上限） | 净粮为负；粮仓开始消耗；**粮仓耗尽后**人口开始减少，净粮赤字越大减得越快 |

> 粮仓作为缓冲：超过软上限不立刻掉人口，而是先耗粮仓储，为玩家留下反应时间（建新农田/解散部分军队）。

---

### C. 造兵消耗人口

- 训练开始时**一次性扣除** `数量 × 兵种.popCost` 的人口。
- 若 `currentPop < 所需消耗`，训练被拒绝，返回错误 `insufficient_population`。
- 被扣除的人口进入「士兵形态」——活着的士兵不归还人口，主动解散才归还（见 E）。
- 军队战死则走伤兵机制（见 D），不是直接归还人口。

---

### D. 伤兵机制（战斗死亡 → 部分恢复为人口）

**触发条件**：战斗结束，某方损失 N 名士兵时。

```
伤兵数 = floor( N × unit.popCost × pop_death_recovery_ratio )
永久阵亡的人口 = N × unit.popCost − 伤兵数
```

**流程**：
1. `伤兵数` 个人口**从士兵状态移入伤兵队列**（entry: `{count, healAt: now + healTime}`）。
2. `healAt` 到达时，`currentPop += count`（人回到城市，但不自动变成士兵，需玩家重新花资源训练）。
3. `永久阵亡的人口` 彻底消失，不进入任何池。

**伤兵池独立**：`woundedPool` 是独立队列，不计入 `currentPop`，也不占粮食软上限（不吃粮）。治愈后才加回 `currentPop`。

**双方各结算**：攻守双方各自向自己的城市发 `population.AddWounded` Command，伤兵回各自城市医疗。

**扩展钩子**：`pop_death_recovery_ratio` 和 `pop_heal_time` 均为全局常量；未来「医院/伤兵营」建筑可通过修改器提升恢复比例或缩短治疗时间（population 模块的派生管线加一层，不改主流程）。

---

### E. 主动解散军队

- 驻守在城内的军队可以主动解散：`currentPop += 解散数量 × unit.popCost`，100% 归还人口；**资源不返还**。
- **出征中的军队不能解散**（在途部队由 movement 模块管辖，不在城内）。

---

### F. 特殊单位的人口处理

| 单位类型 | 人口规则 |
|---------|---------|
| **拓荒者** | 训练消耗 `popCost=5`；派出后**永久消耗**，人口不返还（人随拓荒者去建新村了）。解散无效（出征中不能解散） |
| **首领/元老**（senator/chief） | 与普通士兵相同：战斗死亡走伤兵机制，主动解散归还人口 |

---

### G. 建筑被摧毁后的人口响应

攻城锤/投石机破坏建筑 → 繁荣度下降 + 粮食产量下降：

| 效果链 | 说明 |
|--------|------|
| 繁荣度下降 | 增长速率降低；人口**不被硬砍**，只是增长放缓 |
| 粮食产量下降 | 软上限下降；若当前人口超过新软上限，粮仓开始消耗，最终人口缓慢向新软上限回落 |
| 回落速率 | 由净粮赤字决定（非瞬间崩塌），攻击方破坏建筑的人口代价体现为"城市恢复周期" |

---

### H. 人口的两类隐式作用（文明活力）

人口通过以下两大类路径自动影响全局，无需手动分配劳动力。UI 应明确展示各项加成数字。

---

#### H-① 全城共享劳动力增幅（v2 ω 模型）

**核心设计（v2 变更）**：v1 每栋建筑各自计算劳动比 `r_b = min(1, P/S_b)` 已被替换。v2 改用"全城共享岗位需求"模型：

```
D = Σ S_b(level)      （对城内所有 laborAmplified=1 的建筑求和）
ω = min(1, P / D)    （全城唯一劳动效率比，范围 [0,1]）
```

所有速率类建筑均使用同一个 ω，而非各自独立的劳动比：

```
rate_mult_b = pop_labor_floor + laborBonusMax_b × ω
            = 0.75 + laborBonusMax_b × ω
```

**优点**：
- ω 作为城市整体"劳动力充裕度"，人口在所有建筑间统一共享，不会出现"农田满员但兵营空闲"的奇怪状态
- `GetSnapshot` 返回 `laborRatio = ω`，客户端直接展示"全城劳动效率"
- 新村 ω < 1（人口不足以填满所有建筑的饱和阈值），随城市发展趋向 1

**新村 ω 典型值**：
- 罗马开局（P≈495, D≈500+300+500+500+400=2200+其他）→ ω ≈ 0.23
- 中期城（P≈10870, D≈建筑更大）→ ω 随人口增长趋近 1

##### 三池口粮（v2 新增）

v2 将粮食消耗分为三个独立池，分别上报给 economy 的 `SetUpkeep`：

```
civilian_pop 消耗 = currentPop × popPerCapitaCrop                               /hr
soldier_pool 消耗 = (garrisonPopCost + enRoutePopCost) × popPerCapitaCrop × popSoldierCropRatio   /hr
wounded_pool 消耗 = totalWounded × popPerCapitaCrop × popWoundedCropRatio        /hr
```

- `popSoldierCropRatio=1.0`：士兵与平民等量基础口粮（ratio=1.0）；未来可通过兵种特性调整
- `popWoundedCropRatio=1.0`：伤兵口粮量与平民相同（医疗消耗）
- 所有写路径（consumePop/returnPop/healWounded/addWounded/SetGarrisonPop/SetEnRoutePop）都通过统一的 `reportToEconomy()` 函数同步三个池，防止重复遗漏

##### 阶段递减增长（v2）

增长使用普适的相位递减公式，而非"超过 ref 才衰减"的旧逻辑：

```
scale = (ref / (ref + L))^exp    L = softLimit，ref = 2000，exp = 0.6
growthPerHour = prosperity × popGrowthPerProsperity × scale
```

- 新村 L≈495：scale = (2000/2495)^0.6 ≈ 0.87（增长仍较快）
- 中期 L≈10870：scale = (2000/12870)^0.6 ≈ 0.30（明显减速）
- 晚期 L≈73028：scale = (2000/75028)^0.6 ≈ 0.10（增长已很缓慢）

`settle()` 和 `GetSnapshot` 使用同一个 `calcGrowthScale(softLimit)` helper，保证一致性。

##### 建造速度（城镇中心）

与 v1 相同公式，但 ω 统一来自全城共享：

```
time_mult_pop = 1 − laborBonusMax_main × ω
              = 1 − 0.20 × ω
```

#### H-② 加速伤兵治疗

治疗是速率过程（每批伤兵经历一段恢复时长），符合"劳动力加速速率"原则；但治疗加速不依赖单个建筑，而是用全城人口充裕度（λ）驱动。

定义**充裕比** `λ = min(1.0, currentPop / max(1, soft_limit))`（当前人口与软上限之比）。

```
实际治疗时长 = pop_heal_time / ( 1 + pop_heal_bonus × λ )
             = 3600 / ( 1 + 0.50 × λ )
```

| λ | 治疗时长 | 备注 |
|---|---------|------|
| 1.0（满员） | 3600/1.5 = **2400s（40分钟）** | 人多治疗快 |
| 0.5（半员） | 3600/1.25 = **2880s（48分钟）** | |
| 0（零人口） | 3600/1.0 = **3600s（60分钟）** | 人少治疗慢 |

由 population 模块内部调度器处理伤兵治愈时机（Scheduler 驱动，不用 setInterval）。

#### 两类作用的协同感知

两条路径共同构成「人口 = 文明活力」的整体体验：

```
人口下降
  ├→ 五类速率劳动力不足
  │    ├→ 资源产率下降（最多−25%）→ 经济受损、软上限下移
  │    ├→ 研究速率下降（最多−25%）→ 科技进度延迟
  │    ├→ 练兵速率下降（最多−25%）→ 补兵更慢
  │    ├→ 锻造速率下降（最多−25%）→ 装备升级更慢
  │    └→ 建造加速消失（最多−20%）→ 升级建筑更慢 → 恢复更慢
  └→ 伤兵治疗减速       → 伤兵回血更慢       → 恢复期更长
```

战争造成士兵死亡 → 人口永久流失 → 上述全部路径同时恶化 → 战争有真实代价，不是「打完补兵继续打」。

### 4.2 粮食–人口反馈闭环收敛演算

**这是本系统的核心稳定性证明。** 以下仅对**农田劳动力饱和**论证收敛，其他建筑（学院/练兵/锻造/建造）的劳动力增幅不参与粮食–人口反馈回路，无需另行论证。

**反馈回路（仅涉及农田）**：人口 P 增加 → 农田劳动比提升 → 粮食产率上升 → 软上限 L 提高 → P 有更多增长空间 → P 继续增加...

如果这个循环没有制动，将导致 P 和 L 互相追逐、无限螺旋（失控）。以下证明在给定参数下系统**必然收敛**到唯一稳定均衡点。

#### 农田劳动力饱和公式

等级 L 农田的饱和阈值（`pop_labor_floor=fl=0.75`，`laborBonusMax=0.25`，`laborSaturation_cropland=500`）：

```
S(L) = 500 × prodGrowth^(L−1) = 500 × 1.3^(L−1)

实际粮食产率(L) = F_0(L) × [fl + (1−fl) × min(1, P/S(L))]
               = F_0(L) × [0.75 + 0.25 × min(1, P/S(L))]
```

其中 `F_0(L) = 1000 × 1.3^(L-1)`。

#### 固定点方程

均衡时 P = L（人口正好等于软上限），以 Lv1 单农田为例（`F_0=1000, S=500`，建筑维护 `U_b=7`，无军队维护），整理得：

$$P^* = \frac{F_0 \cdot fl + F_0 \cdot (1-fl) \cdot \frac{P^*}{S} - U_b}{c}$$

其中：$fl$ = 0.75，$S$ = 500，$U_b$ = 7，$c$ = `pop_per_capita_crop` = 2.0。

整理（仅当 P* < S，即未完全饱和时）：

$$P^* = \frac{F_0 \cdot fl - U_b}{c - F_0 \cdot \frac{1-fl}{S}} = \frac{1000 \times 0.75 - 7}{2.0 - 1000 \times \frac{0.25}{500}} = \frac{743}{1.5} \approx 495$$

**收敛条件**：分母 > 0，即 $S > F_0 \cdot \frac{(1-fl)}{c} = \frac{1000 \times 0.25}{2.0} = 125$

当前设计：$S_{Lv1} = 500 \gg 125$，**收敛安全余量 4 倍**。

**稳定性系数**（环路增益）：

$$\text{增益} = \frac{d(\text{软上限})}{dP} = \frac{F_0 \cdot (1-fl)}{c \cdot S} = \frac{1000 \times 0.25}{2.0 \times 500} = 0.25$$

增益 = 0.25 < 1：每轮"人口增长放大效应"只有 25%，每轮迭代误差收缩 75%，**几何级数收敛**。

#### 新村收敛迭代演示（罗马开局，1块Lv1农田，无军队）

从 P=0 出发，追踪软上限迭代轨迹（每一行代表 P 从上一行的 L 开始稳定后的快照）：

| 迭代 | 当前 P | 劳动比 P/S | 粮食产率/hr | 净粮（扣维护）/hr | 软上限 L | 差值 L-P |
|------|--------|-----------|------------|----------------|---------|---------|
| 0 | 0 | 0/500=0 | 750 | 743 | **371.5** | +371.5 |
| 1 | 371.5 | 0.743 | 935.8 | 928.8 | **464.4** | +92.9 |
| 2 | 464.4 | 0.929 | 982.3 | 975.3 | **487.7** | +23.3 |
| 3 | 487.7 | 0.976 | 994.0 | 987.0 | **493.5** | +5.8 |
| 4 | 493.5 | 0.987 | 996.8 | 989.8 | **494.9** | +1.4 |
| 5 | 494.9 | 0.990 | 997.5 | 990.5 | **≈495.3** | ≈0 |

**结论**：5 次迭代后误差 < 0.5，均衡点 P* ≈ 495，与解析解（≈495）一致。每轮差值缩减约 **75%**，符合理论增益 0.25。

#### 为何均衡是稳定的

当 P* ≈ 495（此时 P < S=500，接近饱和临界点）：

- 若外力把 P 推高到 500：此时 P > 软上限（=495），粮仓开始消耗 → P 被向下拉回 495。
- 若外力把 P 压低到 400：此时 P < 软上限（≈471，因劳动比降低），P 向上增长 → 回到 495。

**唯一稳定吸引子**，双侧自愈。

#### 完全饱和后（P ≥ S）的更简单情形

当城市发展到 P >> S（所有农田劳动力饱和），反馈回路断开，软上限退化为简单线性公式：

$$L = \frac{F_{max} - U_b - U_m}{c}$$

此时 L 不依赖 P，是纯粹的「粮食产量决定人口上限」，没有任何反馈复杂性。中/晚期城市均处于此状态（中期 P*=10870 >> S_单农Lv8=2188）。

### 4.3 战斗损失后的伤兵与恢复示例

**场景**：中期村庄，均衡人口 10,870，拥有 2,000 名罗马步兵（popCost=1，upkeep=1）。

**步骤一：出征前状态**
- 训练 2000 步兵时已消耗 2000 pop → `currentPop = 10870`（这是平衡后的状态）
- 软上限 = (25100-360-2000)/2.0 = 11370（扣军队维护后）

**步骤二：战斗结束，损失 500 步兵**

```
伤兵数  = floor(500 × 1 × 0.30) = 150 人  → 进入伤兵队列
永久阵亡 = 500 × 1 − 150       = 350 人  → 彻底消失
```

战后立刻：`currentPop = 10870`（未变，因 pop 在训练时已扣）；`woundedPool = [{count:150}]`

**步骤三：状态调整**
- 剩余兵力：1500，军队维护 = 1500/hr
- 新软上限 = (25100-360-1500)/2.0 = **11620**（比战前更高，因军队维护减少了）
- 当前 P=10870 < 新 L=11620 → 人口开始增长（速率 6000/hr），约 2 分半钟就能增加 250 人

**步骤四：伤兵治愈**
- λ = 10870/11620 ≈ 0.94（近满员）
- 实际治疗时长 = 3600 / (1 + 0.50×0.94) ≈ **2450s（约 41 分钟）**
- `currentPop += 150` → pop 回补 150 人

**净人口损失盘点**（从这场战斗看）：
- 350 人永久阵亡 → **永久损失 350 pop**
- 150 人伤兵经 ~41 分钟治愈后回归 → 有效回收 150 pop
- **实际净损失：350 pop（即 70% × 500）**

对比主动解散（不打仗直接解散）：500 pop 100% 归还，0 永久损失。战争代价得以量化。

**唯一状态归属**：人口相关数据只由此模块拥有，其他模块不得直接读写其 store 集合。

}

  id: string;                     // 任务 id（用于取消）

#### Events（population.ts 发出）

所有 `population.Changed` 事件统一携带以下公共字段（v2 要求）：

```typescript
{
  // ── 公共必带字段 ──
  currentPop: number;      // 当前人口（floor）
  woundedTotal: number;    // 伤兵总数
  totalPop: number;        // currentPop + woundedTotal
  garrisonPop: number;     // 驻守在城内的士兵 popCost 总量
  softLimit: number;       // 当前软上限（≥0，rawSoftLimit clamp）
  growthPerHour: number;   // 当前增长速率（/hr）
  lambdaRatio: number;     // currentPop/softLimit（满员率）
  cropDeficitRate: number; // 日消耗缺口（≥0；>0 表示赤字中）
  inFamine: boolean;       // 是否处于饥荒状态
  laborRatio: number;      // ω（全城劳动效率，0–1）
  // ── 事件专属字段（各事件另加）──
  event: 'famine' | 'death' | 'recovery' | 'healed' | 'consumed' | 'returned' | 'wounded' | 'garrison' | 'enRoute';
}
```

| Event | 时机 | 专属字段 |
|-------|------|---------|
| `population.Changed{event:'famine'}` | 首次进入饥荒 | `reduced, rawSoftLimit` |
| `population.Changed{event:'death'}` | 饥荒持续 tick | `reduced, rawSoftLimit` |
| `population.Changed{event:'recovery'}` | 粮仓转正、退出饥荒 | — |
| `population.Changed{event:'healed'}` | 一批伤兵治愈归队 | `healed` |
| `population.Changed{event:'consumed'}` | ConsumePop | `consumed` |
| `population.Changed{event:'returned'}` | ReturnPop | `returned` |
| `population.Changed{event:'wounded'}` | AddWounded | `added` |
| `population.Changed{event:'garrison'}` | SetGarrisonPop | — |
| `population.Changed{event:'enRoute'}` | SetEnRoutePop | — |

#### Events（population.ts 订阅）

| Event | 来源 | 用途 |
|-------|------|------|
| `building.ProsperityUpdated` | building.ts | 更新繁荣度 → 重算增长速率 |

#### 时间驱动

- **惰性结算**：人口增长与粮食消耗均采用 economy 同款惰性结算模式——`update(now)` 调用时按时间差 `Δt = now - lastTick` 补算，而非每 tick 推进。
- **伤兵治愈**：向 Scheduler 注册 `healAt` 时刻的一次性任务，到时发 `population.HealWounded` 内部命令（禁止模块内用 setTimeout，符合铁律 #3）。
- **软上限变化检测**：每次结算时，若软上限低于当前人口，向 Scheduler 注册「粮仓耗尽后开始减员」逻辑（粮仓容量 / 日消耗速率 = 粮仓耗完时间，届时触发减员循环）。

### 5.4 四条铁律自查

| 铁律 | 遵守情况 |
|------|---------|
| **状态归属唯一** | `currentPop` / `woundedPool` 只在 `population.ts` 的 store 集合里；其他模块通过 Command 读写 |
| **跨模块只传 Command/Event** | military → `population.ConsumeForTraining`；combat → `population.AddWounded`；economy/military/academy/building → `population.GetLaborMult` 或订阅 `population.LaborSnapshotUpdated` Event；没有跨模块直接 import |
| **时间统一走 Scheduler** | 惰性结算（读时补算）+ 伤兵治愈走 Scheduler 注册，不用 setInterval/setTimeout |
| **派生属性对外只给快照** | `prosperity`、`laborMults`、`softLimit`、`lambdaRatio` 均在内部计算，对外 `GetSnapshot` / `GetLaborMult` 只返回结果值 |

## 六、平衡风险与上线监控指标

### 主要风险点

| 风险 | 描述 | 缓解措施 |
|------|------|---------|
| **死亡螺旋** | pop低→产率低→净粮减少→软上限低→pop更难恢复→更低 | 设 `pop_labor_floor=0.75`（产率不低于75%），确保有足量粮食驱动繁荣度增长；新村满员开局也提供初始缓冲 |
| **练兵速率差距过大** | 满员 vs 零人口练兵速度差 33%，大型战争后补兵明显变慢 | 上限 25% 是刻意设计（给战争"代价感"）；若玩家反馈太慢，调低 `laborBonusMax`（barracks/stable/workshop） |
| **学院劳动加速套利** | 玩家专门保留人口不练兵，最大化研究速率 | 无套利空间：高人口意味着更高粮食消耗，自然制约；研究加速是相对的速率增幅，不影响研究树解锁顺序 |
| **士兵无限伤兵刷** | 反复训练-战死-治愈-训练，等效无资源消耗刷军队 | 伤兵只回pop不回士兵；治愈后仍需重新花资源训练，路径不可利用 |
| **拓荒者pop成本阻塞扩张** | 3名拓荒者=15 pop，新村人口<495可能不够 | 新村开局即满员（495+），训练3拓荒者消耗15 pop后剩480+；不构成阻塞 |
| **人口增长过快（晚期）** | 若阶段递减失效，晚期战后分钟级回满 | 已用 `pop_growth_scale_*` + `pop_growth_per_prosperity=5`；目标中期≈1h / 晚期≈2h 补回 350 永久阵亡 |
| **劳动力中期永久满档** | 若 D 远小于 P，ω 长期=1，文明活力失效 | 已提高 laborSaturation，中期目标 ω≈0.5–0.6 |

### 上线后监控指标

| 指标 | 采样方法 | 告警阈值 | 对应调参 |
|------|---------|---------|---------|
| **平均战后pop恢复时间**（补回 350 永久阵亡） | 战报+定时快照 | 中期 &lt;0.5h 或 &gt;3h；晚期 &lt;0.5h 或 &gt;4h | 调 `pop_growth_per_prosperity` / `pop_growth_scale_exp` |
| **军民比与训兵后余量** | 训练前后 softLimit−currentPop | 训兵后余量增大（方向倒置） | 检查 `pop_soldier_crop_ratio` 与 upkeep 守卫 |
| **全城劳动效率 ω** | GetPopulation.laborRatio | 中期均值 &gt;0.95 → 劳动力差异化失效 | 上调 buildings `laborSaturation` |
| **练兵速率感知**（满员vs战损后速度差） | 玩家调研 + 训练时长分布 | >30%反馈"练兵太慢" → 劳动加成过强 | 下调 `laborBonusMax`（barracks/stable/workshop） |
| **拓荒者训练失败率**（insufficient_population） | 训练拒绝日志 | >20% → 新手被pop卡住 | 调低 settler popCost 或提高新村初始pop |
| **粮食软上限贴近率**（P/L 均值）| 每5分钟快照 | <60% → pop没成为有效约束 | 上调 `pop_per_capita_crop` |
| **伤兵治愈利用率**（伤兵治愈量/总阵亡量） | 医疗日志 | <10% → 玩家忽视此机制 | UI优化，或提高 `pop_death_recovery_ratio` |
