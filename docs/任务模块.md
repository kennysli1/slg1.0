# 任务模块

## 事实源与职责

任务定义只在 `config/quests*.csv`：任务线、任务节点、条件、目标、效果、关系边六张表。`infra/config.ts` 读取、校验并编译它们；`modules/tasks.ts` 与同 owner 的 `modules/task/` 按任务 `scope` 保存任务实例、事件推进、交付和任务营地，客户端通过 `task.GetPlayerState` 将任务分成全局任务与当前村庄任务。`task/state.ts` 是 task 集合结构与旧档归一化的唯一位置，`task/catalog.ts` 将六表图按任务汇集并保留旧 `QuestDef` 兼容投影，`task/player-directory.ts` 只经 `player.*` Command 获取归属快照，禁止读取 `player` 或 `player_byvillage` 集合。NPC 对话定义单独位于 `config/dialogues.csv`，由 `modules/dialogues.ts` 按任务代码和触发点创建有序的一次性 session 段落组，不把对话或当前回复写进存档。宝物、PvE、贸易等跨模块结果经既有 Event/窄命令进入任务模块，不能反向写任务状态。

任务是玩家工作区的一部分而不是村庄页面的附属栏。主线任务默认 `scope=global`，全局支线也可显式配置为 `global`；每日任务和当前四个支线任务（s1–s4）为 `scope=village`。全局实例固定存于玩家第一座村（主城）作为锚点，但任务营地在激活/接取时记录 `spawnVillageId`，并以该村当时的坐标生成一套唯一营地；全局任务从任意己方村清理时仍更新同一实例。村庄任务只读取并写入其绑定村，允许其它己方村出兵；进度、任务掉落报告和就绪状态仍回写绑定村，奖励则发到实例最后记录的 `executionVillageId`。聚合快照的 `global` 区块只出现一次，`villages` 区块按村切换；客户端把全局营地合并到玩家所有村的地图缓存，避免任务卡与地图各自保留一套坐标。领取时临时切换当前村不能改写奖励村庄。待处理报告也携带奖励收件村标识。

任务页的菜单层级固定为：全局任务 / 村庄任务（一级）→ 主线、支线、日常（二级）→ 具体任务（三级）。没有任务内容的二级分类自动隐藏，具体任务默认展开。全局区包含主线、全局支线、全局日常和王国任务；村庄区只显示当前操作村的支线和日常。M1 是唯一建村自动激活的主线，后续主线满足前置后进入 `offeredMain`，必须由玩家手动接取，接取后才创建任务实例、营地或其他目标。任务页顶部复用 `VillageList`，切换村庄后只切换村庄区，不能查看、接取或操作其他村的村庄级任务。同一玩家的一次性支线只能由一个村接取；接取时会从该玩家其他村的可接取列表移除。日常任务仍在酒馆/任务页显示和接取，但不计入导航栏、一级/二级菜单的可接取提醒；非日常任务的三级菜单即使展开，任务摘要仍保留“可接取”提醒标记。

酒馆每个任务槽独立刷新：到达 `taskRefreshSec` 刷新周期时，先清空尚未接取的 `offered` 槽位，再按当前酒馆等级的 `taskSideQuestChance`（默认 0.5）决定该槽是否从酒馆触发型支线池抽取，未命中则从日常任务池抽取；任一池为空时使用另一池补位。池内仍按任务 `weight` 加权且同一刷新不会重复。酒馆触发型支线使用 `quest_conditions.csv` 的 `offer/tavern_refresh` 条件，占用 `offered` 槽位；已完成、已放弃、已接取或曾经持有过的支线不会重新进入刷新池。启动恢复和酒馆建成/升级时只补齐空槽，避免重启或改建无故丢弃待接取任务；已接取任务保存在 `active`，不受酒馆刷新影响。`taskRefreshSec` 和 `taskMaxTasks` 也按酒馆等级配置，分别控制刷新间隔与槽位数，均在 `building_levels.csv` 的酒馆行中编辑。

GM 运维命令 `task.GmResetAll` 只清空所有玩家和村庄的任务状态及任务营地（以 `pve` 目录扫描，包含与任务状态脱节的孤儿营地），并重新激活各玩家主城的 M1；不修改资源、建筑、军队、科技、声望或地图其他实体。

任务页签的数字提醒统计玩家聚合快照中 `offeredMain`、`offeredSide` 和非日常 `offered` 的可接受任务数量；酒馆日常仍显示和可接取，但不计入提醒。进行中的任务和待领取奖励不计入。一级/二级菜单折叠时，在对应摘要显示可接受任务数量；展开后非日常三级任务条目仍保留提醒，日常条目不显示提醒。各级 `details` 的展开状态按玩家 id 写入浏览器本地存储，重新进入任务页时恢复；存储不可用时仅退化为本次页面状态。

当前实例会保存 `lineCode` 和 `definitionRevision`；旧实例缺失这两个字段时由任务代码的当前定义惰性补齐。任务定义结构变化属于存档契约变化，需升 `SAVE_SCHEMA_VERSION` 并在 CHANGELOG 标 `[需刷档]`。

## 图模型

```text
quest_lines ──入口──> quests
                         ├── quest_conditions  （何时出现）
                         ├── quest_objectives  （如何达成）
                         ├── quest_effects     （各阶段效果）
                         └── quest_edges ────> 下游 quests
```

- `requires` 边：来源任务交付后，终点才可出现；校验禁止循环。
- `success_unlock` / `failure_unlock`：记录显式分支关系，供审查与后续多阶段运行时扩展；已有特殊任务仍保留其既有事件处理器，避免改表时改变已上线行为。
- 任务可有多条条件、目标和效果。现有运行时将当前单目标玩法编译为兼容定义；新目标/效果类型须先在运行时注册，再写进 CSV。

## 当前主线目标（M1–M16）

主线均为全局任务，实例锚定主城；执行时可从当前己方村庄操作，奖励发放到最后实际执行目标的村庄。M1 仍在建村时自动激活，其余主线满足关系边后进入可接取状态并须手动接受。

门槛类目标由建筑、人口、资源和战争迷雾模块的权威快照推进，任务只保存进度和就绪状态，不复制这些模块的数据。M2 从建造事件计数：只有在接取时真正空着的槽位上首次完成 1 级新建才增加一次；接取前已有建筑被拆除后在原槽位重建不计数，任务期间同一槽位拆建也不重复计数。升级、修复和接取前已在建造队列中的建筑不计数，进度不会因拆除倒退。`explore_tiles` 统计玩家已探索快照与当前城镇/行军视野的并集，因此新账号开局即可拥有初始视野进度。M10 的 `main_base_level` 直接读取实际主基地等级，达到门槛后仍须手动交付；M11 的 offer 条件为主基地 ≥2 级且没有前置任务。
M14 的动态奖励只在交付时读取当前正声望：声望为正时将其归零，每减少 1 点直接加入 2 名佣兵剑士；该任务奖励兵力不登记雇佣兵营地合同，因此无服役期限，也不占人口和粮食。雇佣兵营地购买的兵力仍由营地合同按 `contractSec` 到期移除。M15 的 `reputation_at_most` 在声望变化事件后即时检查，奖励为 10 科技点及粮食产量 +25% 持续 24 小时。M16 的 `reputation_at_least` 同样在声望变化事件后即时检查，交付时通过 `grant_mercenaries` 直接加入 10 名佣兵弓手，无合同和时间限制。M13–M15 归入独立主线“另一边的故事”（入口 M13），M16 保留在“开眼看世界”并以前置 M12 解锁。S5 的击杀进度由 `combat.BattleEnded` 的防守方实际损失推进，跨战斗累加；仅统计 `game_constants.csv:cavalry_unit_codes` 中的兵种，并按其 `units.csv:popCost` 计人口（缺失/零值按 1 计），NPC 服务军队不替玩家完成任务。

每个主线和支线在 `config/dialogues.csv` 都必须同时有 `<code>_accept`（接取）和 `<code>_deliver`（交付）模板。一个对话对象可用相同 `id/code/taskCode/trigger` 配置多行，通过 `segment=1,2,...` 排序；只有显式回复才推进段落，X、遮罩和 Esc 始终关闭整个 session。Accept 的 `accept` 回复成功执行 `task.Accept` 后才推进；`leave` 或关闭不接任务，重新打开仍从第一段开始。M1 与 `after_accept` 等自动等待对话关闭时由客户端调用 `task.ConsumeDialogue` 消费整个 session，不展示后续段，也不会在刷新后重弹。

交付使用“预览—确认”两阶段：任务栏先调用只读 `task.StartDeliver`，服务端解析动态奖励、奖励村庄与完整 deliver 对话，但不改变资源、人口、声望、宝物、军队或任务状态；首段首次点击 `take` 才调用 `task.Deliver` 正式结算，领取后的后续 `take` 只推进客户端对话。领取前关闭会保留待领取任务并在下次从第一段开始；结算请求期间客户端禁止重复点击和关闭。服务端继续按“任务存储村 + 任务代码”互斥，并在锁内重新检查任务、就绪状态、奖励村庄与动态分支。旧数据或异常配置没有可展示交付文本时，`StartDeliver` 返回“任务奖励已准备好 / 收下”的临时默认段，不写回或覆盖 `dialogues.csv`。

S3 的接取后追问独立为 `s3_after_accept`，只有任务接受成功后才排入待弹对话，不属于 `s3_accept` 的段落组。配置中心创建或保存新增支线时会自动补齐接取/交付模板；deliver 段按配置约定使用 `take:收下`。`npcName`/`npcText` 的 `{villageName}` 与 `{fiefName}` 变量由服务端按任务奖励村庄和所属封地渲染，配置中心与 CSV 保留变量名，客户端只接收已替换文本。M1 现有自动接取对话文本保持不变。M8/M9 的成功对话使用默认 `accept`/`deliver`，仅失败分支使用 `*_failure` 触发器。

## 现有任务的特殊处理

`村民的请求`、`调查坐标`、`耀武扬威`涉及 NPC/任务营地、随军军旗或待处理宝物。这些动态对象的生命周期仍由 `tasks.ts` 中的命名处理器拥有；CSV 描述触发、目标、奖励和关系，处理器负责根据玩家实际选择推进状态。不得把坐标、营地 id、宝物实例 id 等玩家态写回配置表。

幸福村是不可重生的 PvE NPC；被战斗清空时由 `combat` 通过 `pve.Remove` 立即移除实体，统一触发 `pve.TargetRemoved`，因此仍在前往该村的商队会从服务端记录的当前行军进度自动返程。任务营地的普通清理不会按通用 `droprate` 抽宝，也不会生成其他任务的专属宝物；只有 S4 在最终清理阶段显式生成“被囚禁的娜塔莉们”，并等待玩家选择。任务卡片展示完成、失败及多阶段分支的资源、宝物和声望结果；S3 完成结算 -1 声望，S4 释放结算 +2 声望，收纳分支失败结算 -2 声望。S4 释放后，任务交付命令返回的奖励对象同时包含资源奖励（500 金币）、声望和宝物，客户端据此完整展示领奖明细。

GM 重新触发已完成的 M8 会先移除上一轮保留的天王老子村实体，再由重新接取流程按当前 CSV/GM 模板生成新的守军和初始库存；M8 的正常成功/失败结算仍保留任务村，供 M9 反击使用。

天王老子村属于任务专属目标，不参与普通 PvE 宝物掉落。`pve.ApplyResult` 会返回目标模板类型，Combat 对 `tianwang_village` 做兜底识别，以兼容旧存档缺失 `task` 标记的情况；铁壁勋章只在 M8/M9 的 `task.Deliver` 奖励路径发放。任务交付在进程内按“任务存储村 + 任务代码”互斥，重复/并发点击不会重复发放奖励。

任务营地默认不因战败而推进或失败；战败事件只记录战报并保留任务营地，若旧存档或并发结算导致实体暂时消失，任务模块会按任务快照坐标恢复。只有任务定义明确增加战败失败规则时，才允许改变这一生命周期；当前任务图没有此类任务。

地图选中任务营地时，客户端从任务实例快照派生并展示关联任务名称、任务说明、全局/村庄任务类型和清理进度；单独的地图标记推送不得覆盖掉这份关联信息。

## GM 与配置中心工作流

任务定义属于配置中心，不属于 GM 状态管理。`/config/quest-modules` 编辑六张任务图表；`/config/dialogues` 编辑 NPC 对话；`/config/quest-graph` 只读审查关系图；`/config/balance` 编辑平衡 CSV。保存前会复制完整配置到临时目录，以 `loadGameConfig` 校验，失败不会写入线上表；成功后写入共享配置、记录 revision/哈希并异步创建 GitHub 配置 PR。兼容旧书签的页面路径会重定向到 `/config/*`，旧的 `/gm/*/data` 和 `/gm/*/save` 接口返回 410，避免误把 GM 当成配置中心。

`/gm/tasks` 只管理任务实例状态：某玩家/村庄是否未触发、可接取、进行中、完成或失败，以及重置、重新触发、回退和任务营地状态。这些操作写入实时 `game.json/WAL`，立即生效，不改变任务定义 CSV。配置 PR 合并后，按 `CLAUDE.md` 的 main-only 部署流程发布；删档只清理进度，不覆盖配置中心的 CSV。`balance_overrides.json` 仅作为一次性迁移输入，迁移成功后改名归档，运行时不再读取。

## 新增或改造任务的步骤

1. 先确定所属任务线；没有合适任务线才在 `quest_lines.csv` 增加一行。
2. 在 `quests.csv` 建立稳定 code，禁止复用已删除任务的 code。
3. 分别添加条件、目标、效果和关系边，并在 GM 图检查所有引用。
4. 若引入新的目标、条件或效果 `kind`，先在 `config.ts` / `tasks.ts` 增加类型、校验和测试；不要用字符串绕过校验。
5. 为触发、放弃、完成、交付、重启恢复和旧存档各补一条服务器测试；涉及宝物/营地时还要覆盖归城、满栏和目标消失。
6. 更新 `config/README.md`、CHANGELOG 和本页长期有效结论，按 `CLAUDE.md` 完成验证、PR、合并与部署。
