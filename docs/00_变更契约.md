# 变更契约（HARD RULES）

> **这是本仓库唯一一份"违反就不让提交"的规矩。** 人和 AI 一视同仁。
> 文档规则由 `npm run guard` 校验；提交钩子按变更范围执行本地验证，PR CI 执行完整测试、Linux 发布布局、产物冒烟与依赖审计，线上发布必须显式执行。

## 为什么要有它

两人 + 多个 AI 并行开发，最先烂掉的不是代码，是**上下文**：

- 每加一个功能就多一篇设计文档，没人删 → AI 每次得读的东西越来越多，最后读不完就开始瞎猜。
- 索引（PROJECT.md 的模块表 / 文档表）写完就不再更新 → AI 读了索引反而被误导，只能全仓扫描。
- 改了存档结构 / 协议但没人记 → 上线才发现要刷档，或新旧客户端打架。

所以本契约只解决一件事：**让 AI 读 2 个文件就能掌握全貌，其余按需下钻**。做法是给文档设预算、设生命周期，并强制索引与代码保持一致。

## R0 · 功能分支开发，主分支只接受评审合并

完整开工、worktree、同步、冲突、PR 和收尾命令见 [`Git协作规范.md`](./Git协作规范.md)，所有人和 AI 必须按该流程执行。

- 所有代码、配置、文档修改都必须在功能分支完成，禁止直接在 `main`/`master` 上修改或提交。
- 开发者可长期复用自己的非 main 开发分支；每个新需求开始前必须 `git fetch --prune origin` 并把最新 `origin/main` 合入该分支。
- 每位开发者必须显式配置自己的 Git 姓名和 GitHub 邮箱；提交闸门拒绝 `.local` / `localhost.localdomain` 机器身份。
- 长期个人分支建议使用 `dev/<owner>`；需要并行隔离时可另建 `<type>/<owner>-<description>` 临时分支。
- 功能分支完成本地验证和提交后推送远程，通过 PR/MR 评审合并到主分支；禁止本地直接推送主分支。
- `npm run guard` 与 Git 提交钩子会拒绝主分支提交，`pre-push` 会拒绝向远程主分支直接推送。

## R1 · 文档分四层，常读的必须短

| 层 | 文件 | 行数上限 | 谁读 |
|----|------|---------|------|
| **L0 入口** | `CLAUDE.md` | **120** | AI 每次必读。只放红线 + 任务路由表 |
| **L1 地图** | `PROJECT.md` | **300** | 接任务时读。全局结构 + 模块清单 + 文档清单 |
| **L2 参考** | `docs/**`（`class: index`） | **300** | 按路由表下钻 |
| | `docs/**`（`class: reference`） | **400** | 同上，常青知识 |
| **L2 设计** | `docs/**`（`class: design`） | 不限行数，但**活跃篇数 ≤ 8** | 只在改对应系统时读 |
| **L3 归档** | `docs/archive/**` | 不限 | **AI 默认不读**，不占预算 |

超预算 = 提交失败。解法只有两个：**精简**，或**拆分并登记到索引**。不许靠豁免。

根文档同样受限：`README.md` ≤ 160 行，只负责"怎么跑起来"；`AGENTS.md` ≤ 40 行，只指向唯一规则入口。深入内容一律指向 `PROJECT.md`。

## R2 · 每篇文档必须有 front-matter

`docs/**` 下每个 `.md` 文件开头必须是：

```yaml
---
class: index | reference | design
status: active | draft | archived
updated: YYYY-MM-DD
owner: design | server | client | ops | art
summary: 一句话说清这篇讲什么（≤ 60 字）
---
```

作用：**AI 扫一遍 summary 就能决定读哪篇**，不用打开正文。这是"渐进式了解"的物理基础。
改了正文就得改 `updated`（guard 会核对：内容变了但日期没变 → 拒绝）。

## R3 · 索引即真相（最重要的一条）

三张索引表必须与磁盘上的真实文件**一一对应**，多一个少一个都提交不了：

| 索引表 | 必须覆盖 |
|--------|---------|
| `PROJECT.md` §四 模块清单 | `packages/server/src/modules/*.ts` 每个文件 |
| `PROJECT.md` §五 文档清单 | `docs/**/*.md` 每篇活跃文档（archive 除外） |
| `config/README.md` | `config/*.csv` 每张表 |

**加了模块不写进清单 = 提交失败。** 这条保证了后来的 AI"读索引 = 知道全貌"，从而不需要全仓扫描。
同时反向校验：索引里写了但文件不存在（死链）也失败。

> 推论：索引只允许有一份。同一份清单不许在两个文件里各写一遍——重复必然漂移。要引用就写"见 PROJECT.md §五"。

## R4 · 规划文档用完即归档

`class: design` 的文档（系统设计推演、重构实现规划）是**一次性消耗品**。对应功能上线后必须：

1. 把里面**长期有效的结论**并入常青文档（`03_架构总览` / `07_扩展与代码规范` / 模块清单的职责列）；
2. `git mv` 原文到 `docs/archive/`，front-matter 改 `status: archived`；
3. 从 `PROJECT.md` 文档清单里移除。

活跃 design 文档超过 8 篇即提交失败——**这个上限就是逼你还债的闹钟**。

## R5 · CHANGELOG 是唯一的历史入口

改动了 `packages/**/src/`（测试除外）或 `config/*.csv` 的提交，**必须**在 `CHANGELOG.md` 的 `## [未发布]` 段里加至少一条。

- 分类固定：`### 新增` / `### 变更` / `### 修复` / `### 移除` / `### 破坏性`
- 需要刷档的改动，条目里必须带 **`[需刷档]`** 标记
- 目的：AI 想知道"最近发生了什么"只读这一个文件，不用去翻 `git log` 猜

## R6 · 三个版本号各管一摊，破坏性变更必须同步升

| 版本号 | 位置 | 什么时候升 |
|--------|------|-----------|
| 应用版本 | `package.json` 的 `version` | 发版时由 `npm run release` 统一改，平时别手动动 |
| 协议版本 `WIRE_VERSION` | `packages/shared/src/wire.ts` | 改了信封结构 / 动作契约就必须升 |
| 存档版本 `SAVE_SCHEMA_VERSION` | `packages/server/src/infra/schema-version.ts` | 改了落盘数据结构（坐标、字段、新集合）就必须升 |

自动校验：
- `wire.ts` 有非注释改动但 `WIRE_VERSION` 没变 → 拒绝
- CHANGELOG 里出现 `[需刷档]` 但 `SAVE_SCHEMA_VERSION` 没升 → 拒绝（反之亦然）
- 升了 `SAVE_SCHEMA_VERSION` 只表示需要迁移评估；只有旧存档确实无法兼容时，才制定并单独授权 `season`/`respawn`/`wipe` 方案。

## R7 · 生产部署只能来自远程 main

- `git commit` 只验证当前暂存快照：guard、按范围构建/lint/类型检查/测试，运行时改动再做隔离生产冒烟；不得连接或改变生产环境。
- `npm run deploy:prod` 可以从任意本地分支发起，但必须读取 `git ls-remote origin refs/heads/main` 的确定 SHA，在临时 worktree 验证并打包该提交。
- 禁止在生产服务器编辑、提交或合并源码；确需远端调试时使用生产目录以外的独立 clone。
- 当前工作区、未提交内容、当前功能分支和本地 main 都不得进入生产包。
- 远端构建写入 `releaseBranch=main` 和 `releaseCommit=<SHA>`；公网 `/version` 必须与目标 SHA 一致，否则回滚。
- 生产目录不是开发工作树：代码发布到 `releases/<SHA>`，`current` 原子切换，持久数据和日志只放在 `shared/`；生产机不保留可操作的 `.git`。
- 正式 `data/game.json` 和日志不进入发布包或代码回滚包。

生产部署所需连接参数默认读取当前腾讯云配置，也可用 `DEPLOY_KEY`、`DEPLOY_HOST`、`DEPLOY_REMOTE`、`DEPLOY_URL` 覆盖。

## 五道自动闸门

| 闸门 | 触发 | 跑什么 | 耗时 |
|------|------|--------|------|
| G1 | `git commit` | 作者/工作区快检 + commit message 规范校验 | < 1 秒 |
| G2 | `git commit` | `npm run guard`：R0 分支保护 + R1–R6 静态文档/版本契约 | < 1 秒 |
| G3 | `git commit` | 按变更范围验证；运行时改动再做隔离的本地生产冒烟 | 秒级～数分钟 |
| G4 | `git push` | 不重复本地高成本测试；由不可绕过的 PR CI 统一验证 | 秒级 |
| G5 | 显式发布 | 只验证并部署 `origin/main`，公网校验 release SHA，失败回滚 | 数分钟 |

首次 clone 后跑一次 `npm install` 即自动装好钩子，并设置 `pull.ff=only`、`fetch.prune=true`、`rerere.enabled=true`。
想手动装：`npm run hooks:install`。

### commit message 规范（G2）

```
<type>(<scope>): <主题>
```

- `type` ∈ `feat` `fix` `docs` `refactor` `perf` `test` `chore` `config` `build` `revert`
- `scope` 可选，写模块名或页面名：`(population)` `(client)` `(gm)`
- 主题用中文，不加句号，整行 ≤ 72 字符
- 破坏性变更写成 `feat(wire)!: ...`，并在 CHANGELOG 的 `### 破坏性` 里说明

### 不允许分支覆盖生产

生产脚本不接受 branch、工作区目录或自定义提交参数。紧急修复也必须合并到远程 main，再显式发布该 main SHA。

## AI 的标准作业流程

任何 AI 接到"改点东西"的任务，按这个顺序走，不许跳步：

1. 读 `CLAUDE.md`（L0，120 行以内）→ 拿到红线和任务路由表
2. 确认当前位于功能分支；若在 `main`/`master`，先创建并切换功能分支
3. 按路由表读 `PROJECT.md` 对应小节（L1）→ 定位到 owner 模块 / 配置表
4. 只读路由表指名的那 1–2 篇 L2 文档 → 拿到细节
5. 动手改代码
6. **同一次提交内**：更新受影响的索引（R3）+ 写 CHANGELOG 条目（R5）+ 该升的版本号（R6）
7. 暂存全部候选文件，确认工作区没有未暂存/未跟踪内容
8. 正常执行 `git commit`；提交信息通过后，commit-msg 钩子按变更范围完成本地验证，运行时改动再执行隔离生产冒烟
9. PR 合并并推送远程 main 后，如需上线再运行 `npm run deploy:prod`

> 第 5 步不是"额外工作"，它是这次改动的一部分。索引没更新的改动 = 没做完的改动。

## 本地自查

```bash
npm run guard          # R1–R6 全查，秒级，随时可跑
npm run verify:changed # 提交闸门使用的按范围快速验证
npm run verify:quick   # 本地完整业务回归（不含 Linux 发布布局）
npm run test:deploy    # 隔离启动生产产物，执行 HTTP + WebSocket 端到端冒烟
npm run verify:commit  # 手动执行提交总闸门（仅本地验证）
npm run deploy:prod    # 显式部署远程 origin/main，并核对公网 release SHA
npm run verify         # CI/发版前完整版（含发布布局、产物冒烟、npm audit）
npm run release        # 定版：未发布段落封版 + 改 version + 打 tag
```
